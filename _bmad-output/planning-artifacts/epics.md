# Zero100_Builderthon - Epic Breakdown

## Overview

이 문서는 Code.presso의 5일 MVP인 근거 기반 채용 핸드오프 시스템을 PRD, Architecture, UX 계약서와 주최측 HR_data에 따라 구현 가능한 에픽과 스토리로 분해하기 위한 요구사항 인벤토리다. 현재 단계에서는 요구사항만 추출했으며, 에픽·스토리 설계는 요구사항 확인 후 진행한다.

## Requirements Inventory

### Functional Requirements

- **FR-001:** 포지션별 평가 기준을 기준 버전 단위로 관리한다.
- **FR-002:** 교정용 표본에서 HR과 HM이 기준별 판단 상태, 판단 사유와 원문 근거를 독립적으로 입력한다. HR 스크리닝과 HM 서류 심사의 판정 어휘를 단계별로 구분한다.
- **FR-003:** HR과 HM의 판단 상태·근거가 다르면 불일치 항목과 충돌 사유를 표시하고, 두 판단을 자동 통합하지 않는다.
- **FR-004:** 미해결 충돌이 있는 기준 버전은 미승인 상태로 유지한다. 미승인 기준의 탐색 결과는 미리보기로만 표시하고 공식 핸드오프 생성을 차단한다.
- **FR-005:** 기준 승인 시 고유 버전 ID를 발급하고 이후 검토 카드와 핸드오프 카드가 이를 참조한다.
- **FR-006:** B2B 영업 매니저 JD의 필수·우대 기준별 매핑 결과에 원문 텍스트 인용구를 연결한다.
- **FR-007:** 인용구에 LlamaParse Markdown의 문단·헤딩·페이지 정보 또는 원본 PDF 위치를 연결한다. 좌표를 얻을 수 없으면 스니펫·페이지·주변 문맥을 대체 위치 정보로 제공한다.
- **FR-008:** 매핑 결과는 AI가 새로 작성한 요약문보다 검토 가능한 원문 근거를 우선 표시한다.
- **FR-009:** 좌측 원문 뷰어와 우측 기준 패널의 스플릿 뷰를 제공한다.
- **FR-010:** 기준 패널의 인용구를 선택하면 원문 위치 또는 스니펫·페이지·주변 문맥 fallback을 즉시 표시한다.
- **FR-011:** 승인된 기준 버전 없이 공식 핸드오프와 최종 판단 기록을 생성하지 않는다. 미승인 결과에는 미리보기와 기준 상태를 표시한다.
- **FR-012:** PDF 지원서를 입력받아 LlamaParse로 Markdown 변환 후 승인된 기준 버전에 따라 처리한다. PDF 원본과 Markdown을 같은 지원서 근거로 연결한다.
- **FR-012a:** 178건 지원 접수 원장과 20건 비식별 이력서 표본을 구분해 사용하고, 178건 전체 원문 PDF 실시간 처리는 보장하지 않는다.
- **FR-012b:** PDF 원본, LlamaParse Markdown, 기준별 인용구와 위치 정보를 지원서 단위로 추적한다. 변환·위치 추출 실패 시 처리 상태와 실패 사유 및 fallback을 제공한다.
- **FR-013:** 검토자가 지원서별 판단 상태와 원문 기반 판단 사유를 저장한다.
- **FR-014:** 핸드오프 카드에 지원서 원문, 적용 기준, 1차 판단 근거, 미검증 질문과 인터뷰 검증 질문 후보를 한 화면에 제공한다.
- **FR-015:** HR 스크리닝과 HM 서류 심사의 판단 차이와 각 단계의 참조 근거를 분리 표시한다.
- **FR-016:** 현업 리더가 핸드오프 카드를 열람하고 인터뷰 검증 질문을 확인한다.
- **FR-017:** 인터뷰 완료 후 최종 결과를 입력하고 서류 단계 초기 가설과 면접 검증 결과를 비교 기록한다.
- **FR-018:** 결정 로그를 기준 버전 ID에 연결해 판단 기준과 근거를 사후 재현한다.
- **FR-019:** 적용 기준, 근거 부족 항목과 검토자 우려를 바탕으로 인터뷰 검증 질문 후보를 여러 개 생성한다. Code.presso의 역량 프레임워크와 질문 은행을 참고한다.
- **FR-020:** 각 질문 후보에 확인 대상 기준 또는 우려 지점, 질문 이유와 참조 근거를 연결한다.
- **FR-021:** 검토자가 질문 후보를 수정·삭제·선택하고, 선택되지 않은 후보는 최종 인터뷰 질문으로 표시하지 않는다.
- **FR-022:** 질문 후보는 자동 합격·탈락이나 새로운 사실 단정이 아니라 서류에서 확인되지 않은 내용을 검증하는 질문이어야 한다.

### NonFunctional Requirements

- **NFR-001 근거 추적성:** 모든 매핑 근거는 원문 위치로 역추적 가능해야 하며 확인할 수 없는 생성 텍스트를 근거로 표시하지 않는다.
- **NFR-002 안전한 실행:** 미승인 기준의 공식 핸드오프·최종 판단을 차단하고 탐색용 미리보기에는 기준 상태를 표시한다.
- **NFR-003 검토 속도:** 지원서 1건의 근거 확인과 판단 사유 기록 시간을 기존 방식과 비교 측정한다. 2분 이내는 보조 검증 지표로 둔다.
- **NFR-004 대량 입력:** 178건 원장과 20건 이력서 표본을 구분해 처리·오류 상태를 표시하며 178건 전체의 원문 PDF 실시간 처리는 MVP 범위가 아니다.
- **NFR-005 감사 가능성:** 기준 버전, 검토자, 판단 사유, 참조 근거와 변경 시점을 기록한다.
- **NFR-006 데모 데이터 안전:** 발표에는 비식별 또는 합성 지원서만 사용하고 실제 개인정보를 사용하지 않는다.
- **NFR-007 모델·비밀값 관리:** MVP와 베이스라인 모델은 `gpt-5.6-luna`를 사용하되 실제 사용 시 API 스냅샷을 확인·고정한다. API 키와 base URL은 서버 환경변수 또는 `.env`로만 관리하며 저장소·브라우저에 노출하지 않는다.

### Additional Requirements

- 주최측 `HR_data`를 도메인 정본으로 사용한다. 데모 포지션은 `B2B 영업 매니저 5년 이상 ver.4`이며 3년 이상 JD와 동시 지원은 MVP에서 제외한다.
- 178건 원장, 15건 판단 사례, 20건 비식별 이력서 표본은 후보 토큰과 표본 매핑표를 통해 연결한다. 재식별·외부 재배포를 하지 않는다.
- HR 스크리닝과 HM 서류 심사의 실제 판정 문자열·단계 상태·필드 의미를 제공 자료와 정확히 맞춘다. HR 불합격 사유는 복수 선택 가능하고 HM 서류 결론은 단계별 근거와 최종 결론을 구분한다.
- 구현 구조는 5일 MVP에 맞춘 계층형 모듈러 모놀리스다. 프론트엔드는 Next.js/React/Tailwind CSS, 백엔드는 FastAPI/Pydantic, 저장소는 SQLite와 PDF 파일 저장소를 사용한다.
- 문서 처리 파이프라인은 `PDF → LlamaParse → Markdown Normalizer → gpt-5.6-luna → Location Resolver` 순서를 따른다. 처리 실패는 완료 결과로 노출하지 않는다.
- PDF 원본, LlamaParse Markdown, 정규화 Markdown과 지원서별 처리 실행을 보존한다. 실행 시 모델, 단계, 시각, 성공·실패 상태와 오류를 기록하고 재처리 결과가 기존 완료 결과를 덮어쓰지 않게 한다.
- 브라우저는 FastAPI를 통해서만 데이터와 PDF에 접근한다. 서버에서 역할·기준 버전·승인 상태를 확인하고 다른 검토자의 로그는 수정할 수 없게 한다.
- 핵심 상태를 기준 버전(`DRAFT`, `APPROVED`, `ARCHIVED`), 검토(`FULFILLED`, `PARTIALLY_FULFILLED`, `UNFULFILLED`, `UNVERIFIABLE`), 처리(`RECEIVED`, `PARSING`, `MAPPING`, `COMPLETED`, `FAILED`), 충돌(`OPEN`, `RESOLVED`), 질문(`CANDIDATE`, `SELECTED`, `DELETED`)으로 관리한다.
- 질문 후보는 핸드오프에 연결된 독립 리소스로 저장한다. 원래 질문과 수정본을 보존하고 soft delete하며, HR/HM이 수정·삭제하고 현업 리더가 선택한 후보만 최종 핸드오프에 포함한다.
- 질문 생성은 역량 프레임워크와 질문 은행의 BEI·SJT·기술/지식 질문 규칙을 준수한다. 구체적인 경험·행동·상황을 묻고, 질문 이유·평가 기준·참조 근거·후속 탐침을 연결하며 차별 소지 질문을 생성하지 않는다.
- 공식 핸드오프 생성과 최종 결정은 승인 기준, 처리 완료, 근거와 검토 로그가 모두 있을 때만 하나의 서버 트랜잭션으로 수행한다. 최종 결정은 사람이 직접 입력한다.
- 발표 데모는 승인된 기준 확인 10초, 대표 지원서 선택 10초, 근거 확인 25초, 의견 차이 확인 15초, 핸드오프 열기 10초, 질문 후보 조정 20초의 약 90초 흐름을 지원한다.
- 발표 제출물은 실제 클릭 가능한 데모, 1~2분 데모 영상, 문제 정의 카드, 설계 요약 1장, 범용 LLM 베이스라인 비교 컷, 레포·배포 링크다. 자동 합격·탈락·랭킹과 ATS 전체 대체는 구현하지 않는다.

### UX Design Requirements

- **UX-DR1:** 승인 기준, 포지션, 버전, 승인 상태와 현재 역할을 전역 `context-bar`에서 유지한다.
- **UX-DR2:** `workflow-nav`로 기준 교정·검토·핸드오프의 완료·현재·잠김 상태를 텍스트로 표시하고 잠긴 단계의 선행 조건 이동을 제공한다.
- **UX-DR3:** `calibration-matrix`에서 HR·HM의 독립 입력과 충돌 행, 양쪽 근거 및 해결 사유를 보여준다.
- **UX-DR4:** 승인 전 `gate-banner`에 차단 이유와 남은 조건을 표시하고 단순 비활성 버튼만으로 상태를 전달하지 않는다.
- **UX-DR5:** 지원서 목록의 `application-row`와 `processing-stepper`에서 처리 상태·실패 단계·실패 사유·마지막 성공 산출물을 표시한다.
- **UX-DR6:** PDF 업로드 형식 오류, 처리 중 부분 결과 차단, 실패 결과의 안전한 표시를 제공한다.
- **UX-DR7:** `evidence-split-view`에서 원문과 기준 패널을 독립 스크롤하고 `active_citation_id`를 양쪽에 동기화한다.
- **UX-DR8:** `document-viewer`는 인용구 선택 시 위치로 이동하며 좌표가 없으면 스니펫·페이지·문맥 fallback을 제공한다.
- **UX-DR9:** `evidence-card`와 `review-control`에서 기준·인용구·위치·근거 없음 상태·검토 상태·판단 사유를 함께 다룬다.
- **UX-DR10:** `reviewer-comparison`은 HR·HM의 판단과 근거를 독립 열로 표시하고 타인의 로그를 읽기 전용으로 유지한다.
- **UX-DR11:** `handoff-card`는 승인 기준·처리 완료·근거·검토 로그가 있을 때 공식 생성되며 카드 ID·버전·생성 시각을 표시한다.
- **UX-DR12:** `question-candidate`에서 원문 질문·현재 수정본·질문 이유·연결 기준·참조 근거·선택 상태를 표시하고 HR/HM 수정·soft delete 및 현업 리더 선택을 구분한다.
- **UX-DR13:** `verification-comparison`에서 서류 가설과 면접 결과를 분리 입력하고 최종 결정은 별도 명시적으로 저장한다.
- **UX-DR14:** `audit-timeline`에서 행위자·시각·기준 버전·참조 근거와 과거 이벤트를 읽기 전용으로 확인한다.
- **UX-DR15:** 모든 비동기 처리·저장·승인·생성·결정 결과를 `live-region`과 화면의 지속 텍스트로 알린다.
- **UX-DR16:** 폼의 `field-control`, `error-summary`, `confirmation-dialog`를 통해 레이블·도움말·입력 보존·오류 링크·안전한 취소·중복 제출 방지를 제공한다.

**Then** 시스템은 LlamaParse Markdown과 필요한 정규화 Markdown을 지원서 처리 실행에 저장하고 원본 PDF와 동일 지원서의 산출물로 연결해야 한다.

**Given** PDF 파싱 또는 Markdown 변환이 실패했을 때
**When** 서버가 실패를 기록하면
**Then** 해당 지원서를 `FAILED`와 실패 단계·사유로 표시하고 `COMPLETED`로 가장하지 않으며, 이미 저장된 원본과 마지막 성공 산출물은 보존해야 한다.

**Given** 브라우저에서 지원서 업로드를 수행할 때
**When** 외부 파서 API를 호출해야 한다면
**Then** LlamaParse API 키와 서버 파일 경로는 브라우저에 노출하지 않고 서버 환경변수 또는 `.env`에서만 사용해야 한다.

**Given** 178건 지원 접수 원장에는 존재하지만 대응하는 PDF 표본이 제공되지 않은 후보일 때
**When** HR이 처리 목록을 조회하면
**Then** 시스템은 해당 행을 `원장 데이터만 있음`으로 표시하고 PDF 파싱·근거 매핑·원문 검토 대상으로 처리하지 않아야 한다.

**Given** 후보 토큰에 대응하는 PDF 표본과 표본 매핑 정보가 있을 때
**When** HR이 해당 표본을 처리하면
**Then** 시스템은 표본 매핑표의 후보 토큰을 원장 `이름` 열과 조인하고 채널·포지션·지원일·판정 메타데이터를 연결해야 한다.

### Story 2.2: 기준별 원문 인용구 매핑

As a 하이어링 매니저(HM),
I want 승인 또는 Draft 기준의 각 요건에 연결된 지원서 원문 인용구와 위치 정보를 확인하고 싶다,
So that AI의 요약이 아닌 실제 지원서 문맥을 근거로 직무 적합성을 검토할 수 있다.

**Acceptance Criteria:**

**Given** 처리 완료된 지원서의 LlamaParse Markdown과 B2B 영업 매니저 기준 버전이 있을 때
**When** 근거 매핑 파이프라인이 실행되면
**Then** 시스템은 각 필수·우대 기준에 대해 매핑 결과를 만들고 지원서 ID, 기준 버전 ID, 처리 실행 ID를 함께 저장해야 한다.

**Given** 기준 항목에 매핑된 근거가 있을 때
**When** 매핑 결과를 조회하면
**Then** 인용구는 정규화 Markdown에서 실제로 확인되는 원문 부분 문자열이어야 하며, AI가 새로 작성한 요약문을 원문 근거로 표시하지 않아야 한다.

**Given** 원문 인용구가 정규화 Markdown에서 확인될 때
**When** 위치 정보를 저장하면
**Then** 가능한 경우 페이지·문단·헤딩 정보를 인용구에 연결하고 원본 PDF와 Markdown 양쪽에서 해당 지원서 근거를 추적할 수 있어야 한다.

**Given** PDF 좌표 또는 정확한 위치를 안정적으로 확보할 수 없을 때
**When** 매핑 결과를 생성하면
**Then** 시스템은 이를 매핑 성공으로 가장하지 않고 스니펫·페이지·주변 문맥을 `문맥 보기` fallback으로 제공해야 한다.

**Given** 기준 항목에 원문에서 확인 가능한 근거가 없을 때
**When** 매핑 결과를 표시하면
**Then** `원문에서 확인 가능한 근거가 없습니다` 또는 `확인 불가` 상태를 명시하고 빈 인용구나 추정 문장을 만들지 않아야 한다.

**Given** 매핑 결과가 `DRAFT` 기준 버전에 연결되어 있을 때
**When** 사용자가 결과를 조회하면
**Then** 결과를 `미리보기` 또는 `탐색용`으로 표시하고 승인된 공식 결과로 오인할 수 있는 표현을 사용하지 않아야 한다.

**Given** 매핑 중 특정 기준의 추출 또는 위치 연결에 실패했을 때
**When** 서버가 처리 결과를 저장하면
**Then** 실패 기준과 사유를 보존하고 성공한 다른 기준의 결과와 구분하며 실패 결과를 완료된 근거처럼 표시하지 않아야 한다.

### Story 2.3: 스플릿 뷰와 텍스트 검색 하이라이트

As a 하이어링 매니저(HM),
I want 기준별 인용구를 클릭해 지원서 원문에서 해당 텍스트를 바로 찾고 하이라이트하고 싶다,
So that PDF 좌표 오류에 의존하지 않고 인용구와 실제 문맥의 일치 여부를 빠르게 확인할 수 있다.

**Acceptance Criteria:**

**Given** 처리 완료된 지원서와 기준별 매핑 결과가 있을 때
**When** HM이 근거 검토 화면을 열면
**Then** 좌측에는 PDF 원문 또는 LlamaParse Markdown 문서 뷰어를, 우측에는 기준별 `evidence-card`를 표시하고 두 패널의 지원서·기준 버전 컨텍스트를 일치시켜야 한다.

**Given** 우측 `evidence-card`에 정규화 Markdown 원문 인용구가 표시되어 있을 때
**When** HM이 인용구를 클릭하면
**Then** 시스템은 `active_citation_id`를 변경하고 프론트엔드 텍스트 검색 하이라이트(`react-highlight-words` 또는 `window.find()`)로 좌측 문서의 동일 텍스트를 찾아 해당 위치로 이동·하이라이트해야 한다.

**Given** 인용구의 PDF 좌표를 확보할 수 없을 때
**When** HM이 해당 인용구를 선택하면
**Then** 좌측 문서에서 좌표 계산을 시도해 실패한 것으로 표시하지 않고 스니펫·페이지·주변 문맥을 `문맥 보기`로 보여주며 선택된 인용구를 확인할 수 있어야 한다.

**Given** 저장된 인용구가 문서 뷰어의 텍스트와 일치하지 않을 때
**When** HM이 인용구를 선택하면
**Then** 시스템은 엉뚱한 텍스트를 하이라이트하거나 성공으로 표시하지 않고 일치 실패 상태와 확인 가능한 스니펫·문맥을 표시해야 한다.

**Given** 좌측 문서와 우측 기준 패널이 열린 상태일 때
**When** HM이 어느 한 패널을 스크롤하거나 다른 기준 카드를 선택하면
**Then** 두 패널은 독립적으로 스크롤되고 현재 `active_citation_id`와 입력 중인 판단 내용은 유지되어야 한다.

**Given** HM이 키보드로 근거 검토 화면을 사용할 때
**When** 기준 카드에 포커스한 뒤 Enter 또는 Space를 입력하면
**Then** 마우스 클릭과 동일하게 원문 검색·포커싱·하이라이트를 실행하고, 위치 변경 결과를 텍스트로 접근 가능하게 알려야 한다.

**Given** 근거 검토 화면에서 매핑 상태를 표시할 때
**When** HM이 기준별 결과를 확인하면
**Then** `충족`, `부분 충족`, `미충족`, `확인 불가`와 근거를 표시하되 점수·순위·합격 확률 또는 자동 합격·탈락 결론을 제공하지 않아야 한다.
## Epic 3: 근거 기반 핸드오프와 인터뷰 검증

HR·HM의 판단 차이를 보존한 핸드오프 카드를 만들고, 근거 연결형 인터뷰 질문 후보를 수정·삭제·선택한 뒤 면접 결과와 최종 사람의 결정을 기록한다.

**FRs covered:** FR-013~FR-022

구현 경계: 5일 MVP에서는 질문 후보와 면접 결과를 핸드오프 카드 테이블에 JSON 형태로 저장하는 flattening 방식을 사용하되, 원문 근거와 결정 로그의 추적성은 유지한다.

### Story 3.1: 판단 로그와 HR·HM 의견 차이 기록

As a 채용 담당자(HR) 또는 하이어링 매니저(HM),
I want 지원서에 대한 나의 판단 상태·사유·참조 근거를 저장하고 다른 검토자의 판단과 비교하고 싶다,
So that 핸드오프 전에 각 단계의 판단 맥락과 의견 차이를 그대로 보존할 수 있다.

**Acceptance Criteria:**

**Given** 승인된 기준 버전과 처리 완료된 지원서의 기준별 원문 근거가 있을 때
**When** HR 또는 HM이 자신이 담당한 검토 단계의 상태, 판단 사유와 참조 인용구를 저장하면
**Then** 시스템은 검토자·역할·지원서·기준 항목·`criteria_version_id`·저장 시각을 포함한 독립 판단 로그를 저장해야 한다.

**Given** HR과 HM의 판단 로그가 같은 지원서에 존재할 때
**When** 검토자가 의견 비교를 열면
**Then** HR 스크리닝과 HM 서류 심사의 상태·사유·참조 근거를 서로 다른 영역으로 표시하고, 상태·위치·근거가 다른 항목은 의견 차이로 표시해야 한다.

**Given** HR과 HM의 판단이 서로 다를 때
**When** 의견 차이를 조회하면
**Then** 시스템은 어느 한쪽의 판단을 대표 결론으로 자동 선택하거나 두 판단을 하나의 결론으로 통합하지 않고 양쪽 원문 근거를 함께 보여줘야 한다.

**Given** 현재 검토자가 다른 검토자의 판단 로그를 조회할 때
**When** 비교 화면에서 로그를 확인하면
**Then** 다른 검토자의 원래 판단·사유·참조 근거는 읽을 수 있지만 수정·삭제할 수 없어야 한다.

**Given** HR 또는 HM이 지원서 전체의 전형 단계 판정을 입력할 때
**When** 단계별 지원서 판정 어휘를 선택하면
**Then** 시스템은 HR 스크리닝 판정과 HM 서류 심사 판정을 서로 다른 Document 레벨 값으로 저장하고, 실제 회사의 단계별 판정 체계를 구분해 제공하며 서로 다른 단계의 값을 잘못 저장하지 않아야 한다.

**Given** 검토자가 판단 사유를 저장할 때
**When** 원문 인용구 또는 확인 불가 상태를 지정하지 않았다면
**Then** 시스템은 근거 없는 판단을 공식 검토 로그로 저장하지 않고 필요한 근거 또는 `확인 불가` 상태 입력을 안내해야 한다.

**Given** 판단 로그를 저장하거나 수정할 때
**When** 저장이 완료되면
**Then** 현재 판단값은 유지하되 기존 값을 덮어쓰지 않고 `ReviewLog.edit_history` JSON 배열에 이전 값·변경 값·행위자·시각·사유를 추가하여 감사 기록에서 추적할 수 있어야 한다.

**Given** 판단 상태를 표시할 때
**When** 검토자가 결과를 확인하면
**Then** 각 개별 기준(Item)에는 `충족`, `부분 충족`, `미충족`, `확인 불가`를 사람의 검토 상태로 표시하고, 지원서(Document)·전형 단계 판정과 혼합하지 않으며 점수·순위·합격 확률 또는 자동 합격·탈락 결론을 제공하지 않아야 한다.

### Story 3.2: JSON 기반 핸드오프 카드 생성

As a 현업 리더(LEAD),
I want 지원서의 원문·기준·검토 판단·의견 차이를 하나의 핸드오프 카드로 확인하고 싶다,
So that 별도 채널을 오가지 않고 인터뷰 전에 후보자의 근거와 확인할 지점을 파악할 수 있다.

**Acceptance Criteria:**

**Given** 승인된 기준 버전, 처리 완료된 지원서, 기준별 근거와 HR·HM 검토 로그가 모두 존재할 때
**When** LEAD가 공식 핸드오프 카드 생성을 요청하면
**Then** 시스템은 핸드오프 카드를 생성하고 지원서 ID·승인된 `criteria_version_id`·생성자·생성 시각을 저장해야 한다.

**Given** 기준이 미승인 상태이거나 지원서 처리가 완료되지 않았거나 근거·검토 로그가 누락되어 있을 때
**When** LEAD가 공식 핸드오프 카드 생성을 요청하면
**Then** 시스템은 생성을 차단하고 누락된 조건을 각각 표시하며 카드나 질문 후보를 부분 결과로 만들지 않아야 한다.

**Given** 공식 핸드오프 카드가 생성되었을 때
**When** LEAD 또는 권한 있는 사용자가 카드를 열면
**Then** 지원서 원문 또는 확인 가능한 문맥, 적용 기준, HR·HM의 단계별 판단·사유·참조 근거, 의견 차이, 근거 부족 항목과 미검증 질문을 한 화면에서 확인할 수 있어야 한다.

**Given** 핸드오프 카드의 질문 후보와 면접 검증 결과를 저장해야 할 때
**When** MVP 저장 구조를 구성하면
**Then** 시스템은 이를 별도의 질문·검증 관계형 테이블로 분리하지 않고 `HandoffCard`의 JSON payload에 저장하며, 원본 질문·현재 수정본·선택 상태·초기 가설·면접 결과를 구분할 수 있어야 한다.

**Given** 핸드오프 카드 JSON payload에 원문 근거와 검토 판단을 저장할 때
**When** 카드 내용을 조회하면
**Then** 각 근거·판단이 원래 지원서 ID, 기준 항목 ID, `criteria_version_id`와 연결되어야 하며 JSON flattening 때문에 추적성이 사라지지 않아야 한다.

**Given** 동일 지원서와 기준 버전에 대해 이미 공식 핸드오프 카드가 존재할 때
**When** LEAD가 다시 생성 요청을 보내면
**Then** 시스템은 중복 카드를 만들지 않고 기존 카드와 현재 생성 상태를 표시해야 한다.

**Given** 카드 생성 요청이 처리 중이거나 실패했을 때
**When** LEAD가 화면을 확인하면
**Then** 중복 요청을 막고 대상 지원서·기준 버전을 고정하며 실패 사유를 표시하고 성공하지 않은 카드나 질문 후보를 성공 결과처럼 보여주지 않아야 한다.

**Given** 핸드오프 카드가 생성되었을 때
**When** 감사 기록을 조회하면
**Then** 카드 생성자·생성 시각·참조 기준 버전·참조 근거를 확인할 수 있고, 카드의 판단 내용을 AI가 자동 결론으로 바꾸지 않아야 한다.

### Story 3.3: 근거·질문 은행 기반 인터뷰 질문 후보 관리

As a HR 또는 HM 검토자와 현업 리더(LEAD),
I want 지원서의 미검증 근거와 Code.presso 질문 은행의 실제 사용 이력에 기반한 인터뷰 질문 후보를 검토·조정하고 싶다,
So that 범용적이고 뻔한 질문 대신 이 후보자에게 확인해야 할 직무 관련 질문을 사람이 선택해 사용할 수 있다.

**Acceptance Criteria:**

**Given** 공식 핸드오프 카드에 승인된 기준, 근거 부족 항목, 검토자의 우려와 원문 근거가 저장되어 있을 때
**When** 질문 후보 생성을 요청하면
**Then** 서버는 `gpt-5.6-luna`를 사용해 지원서의 기준·근거·우려를 입력으로 전달하고, 정확한 질문 개수와 무관하게 하나 이상의 후보 생성을 시도해야 한다.

**Given** Code.presso의 `question-bank`에 과거 면접에서 실제 사용된 질문·의도·평가 포인트·후속 질문 이력이 있을 때
**When** 질문 후보 생성 프롬프트를 구성하면
**Then** 시스템은 현재 지원서의 관련 역량과 질문 유형에 맞는 실제 사용 이력을 Few-shot 예시로 주입하고, 무관한 직군의 질문이나 예시를 무차별적으로 사용하지 않아야 한다.

**Given** Few-shot 예시와 현재 지원서의 원문 근거가 함께 제공될 때
**When** AI가 질문 후보를 생성하면
**Then** 과거 질문의 스타일·의도·검증 구조를 참고하되 현재 지원서에 없는 경험이나 사실을 단정하지 않고 후보자의 근거 부족 항목 또는 우려를 확인하는 새로운 질문으로 작성해야 한다.

**Given** 질문 후보가 생성되었을 때
**When** HR·HM 또는 LEAD가 후보를 조회하면
**Then** 각 후보에 질문 문장, 질문 이유, 연결된 평가 기준 또는 우려 지점, 참조 원문 근거, 질문 유형과 선택 상태를 함께 표시해야 한다.

**Given** 생성된 질문 후보를 품질 기준으로 검토할 때
**When** 후보를 저장하면
**Then** 질문은 구체적인 경험·행동·상황을 묻고 인터뷰 답변으로 검증 가능하며 비유도적·공정하고 중복이 적어야 하며, 지원자의 보호 특성·사생활을 묻거나 자동 합격·탈락을 유도하는 질문은 저장하지 않아야 한다.

**Given** 질문 후보가 핸드오프 카드 JSON payload에 저장될 때
**When** 후보를 저장하면
**Then** 원래 생성된 질문, 현재 수정본, 질문 이유, 연결 기준·근거, 선택 상태와 생성 시각을 구분해 보존해야 한다.

**Given** 질문 후보가 생성된 뒤 수정이 필요할 때
**When** HR 또는 HM이 질문을 수정하거나 삭제하면
**Then** 현재 질문만 수정하고 원래 질문과 변경 이력을 보존하며, 삭제는 `DELETED` 상태로 처리해 기본 후보 목록에서 숨겨야 한다.

**Given** 질문 후보 목록에 `CANDIDATE`, `SELECTED`, `DELETED` 상태가 있을 때
**When** LEAD가 인터뷰에 사용할 질문을 선택하면
**Then** LEAD가 선택한 후보만 `SELECTED`로 표시하고 최종 핸드오프 질문 목록에 포함하며 선택되지 않았거나 삭제된 후보는 최종 목록에 포함하지 않아야 한다.

**Given** 질문 후보 생성이 실패하거나 연결 가능한 근거가 없을 때
**When** 사용자가 결과를 조회하면
**Then** 시스템은 질문을 사실처럼 만들어내거나 자동 결론으로 대체하지 않고 실패 사유 또는 근거 부족 상태를 표시해야 한다.

**Given** 정확한 질문 후보 개수가 아직 확정되지 않았을 때
**When** 후보 생성과 화면을 구현하면
**Then** 정확한 개수를 코드·데이터 계약에 고정하지 않고 발표 화면과 구현 범위를 확인한 뒤 결정할 수 있어야 한다.

### Story 3.4: 면접 검증 결과와 최종 결정 기록

As a 현업 리더(LEAD),
I want 선택한 인터뷰 질문에 대한 실제 검증 결과와 최종 사람의 결정을 핸드오프 카드에 기록하고 싶다,
So that 서류 단계의 가설이 면접에서 확인되었는지 비교하고 결정의 근거를 나중에 다시 확인할 수 있다.

**Acceptance Criteria:**

**Given** 공식 핸드오프 카드와 LEAD가 선택한 인터뷰 질문이 있을 때
**When** 인터뷰 후 LEAD가 질문별 검증 결과를 저장하면
**Then** 시스템은 질문, 연결된 기준·근거, 서류 단계의 초기 가설, 실제 면접에서 확인된 결과, 기록자와 기록 시각을 함께 저장해야 한다.

**Given** 서류 단계의 우려 또는 근거 부족 항목이 핸드오프 카드에 있을 때
**When** 면접 검증 결과를 조회하면
**Then** 초기 가설과 면접 결과를 서로 다른 영역으로 표시하고, 면접 결과가 서류 단계 판단을 자동으로 덮어쓰거나 소급 변경하지 않아야 한다.

**Given** 선택된 질문과 면접 검증 결과가 핸드오프 카드에 존재할 때
**When** LEAD가 최종 결정 화면을 열면
**Then** 시스템은 선택 질문, 검증 결과, 서류 가설, HR·HM 판단 근거를 한 화면에서 확인할 수 있게 해야 한다.

**Given** 승인된 기준 버전, 공식 핸드오프 카드와 필요한 면접 검증 결과가 존재할 때
**When** LEAD가 최종 결정과 결정 사유를 명시적으로 저장하면
**Then** 시스템은 사람이 입력한 결정값·사유·행위자·시각·`criteria_version_id`를 `DecisionRecord` 정보로 저장해야 하며, 결정값 드롭다운에는 주최측 공식 어휘인 `채용`, `미채용`, `종료`, `인재풀 등록`만 제공해야 한다.

**Given** 기준이 미승인되었거나 공식 핸드오프가 없거나 필수 면접 검증 결과·결정 사유가 누락되어 있을 때
**When** LEAD가 최종 결정을 저장하려 하면
**Then** 시스템은 저장을 차단하고 누락된 조건을 안내하며 자동 합격·탈락 결정을 대신 저장하지 않아야 한다.

**Given** 면접 검증과 최종 결정 정보를 저장해야 할 때
**When** MVP 저장 구조를 적용하면
**Then** 질문별 검증 결과와 최종 결정 정보를 별도 관계형 테이블로 확장하지 않고 `HandoffCard` JSON payload에 저장하되, 질문·기준·근거·행위자·시각과의 연결을 유지해야 한다.

**Given** 면접 검증 결과 또는 최종 결정이 수정될 때
**When** 저장이 완료되면
**Then** 현재 값을 갱신하되 이전 값·변경 값·행위자·시각·사유를 카드 JSON의 변경 이력에 추가하고 기존 기록을 삭제하지 않아야 한다.

**Given** 최종 결정이 저장되었을 때
**When** 감사 기록을 조회하면
**Then** 승인 기준, 핸드오프, 선택 질문, 초기 가설, 면접 검증 결과와 최종 사람의 결정을 시간순으로 확인할 수 있어야 하며 AI가 결정한 것처럼 표시하지 않아야 한다.
