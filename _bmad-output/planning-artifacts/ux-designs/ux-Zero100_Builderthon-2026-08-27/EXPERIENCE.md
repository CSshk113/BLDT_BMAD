# Evidence Handoff — Experience Spine

## Foundation

데스크톱 우선 반응형 웹이다. Next.js·React·Tailwind CSS 위에 프로젝트 전용 컴포넌트 계층을 둔다. `DESIGN.md`가 시각 정체성을 소유하고, 이 문서는 정보 구조·행동·상태를 소유한다.

제품의 기본 단위는 하나의 포지션, 하나의 `criteria_version_id`, 하나 이상의 지원서다. 공식 흐름은 `calibration → review → handoff`이며 승인 게이트를 우회하지 않는다. [ASSUMPTION] 5일 MVP는 라이트 모드만 제공한다.

Architecture Spine이 역할·상태·API 게이트의 정본이다. PRD addendum, 발표 요약, 이후 생성되는 mockup·wireframe·import가 이 문서나 `DESIGN.md`와 충돌하면 Architecture Spine과 두 UX spine 순으로 우선한다.

## Information Architecture

| 표면 | 진입 | 목적 | 주요 역할 |
|---|---|---|---|
| 기준 교정·승인 | 앱 시작 / `workflow-nav` | 기준 버전, 독립 표본 검토, 충돌 해결, 승인 | HR(교정·승인), HM(독립 표본 검토) |
| 지원서 처리 목록 | 교정 완료 후 | PDF 업로드, 처리 상태, 오류, 대표 지원서 선택 | HR |
| 근거 검토 | 지원서 행 선택 | 원문·기준별 인용구 확인, 상태·판단 사유 기록 | HM, HR |
| 이견 비교 | 근거 검토 내 탭 | 두 검토자의 상태·근거·사유를 분리 비교 | HR, HM, LEAD |
| 핸드오프 | 검토 완료 / `workflow-nav` | 적용 기준, 근거, 이견, 미검증 항목, 질문 후보 확인 | LEAD |
| 면접 검증·최종 결정 | 핸드오프 내 다음 단계 | 초기 가설과 면접 결과 비교, 사람의 최종 결정 기록 | LEAD |
| 감사 기록 | 각 표면의 기록 링크 | 기준 버전·행위자·근거·변경 시점 재현 | 역할별 읽기 |

`workflow-nav`는 세 상위 단계만 보여준다. `context-bar`는 포지션, 기준 버전, 승인 상태, 현재 역할을 모든 작업 표면에서 유지한다. [ASSUMPTION] MVP 데모에서는 인증을 대신하지 않는 `데모 역할 전환`을 제공하고 명시적으로 데모 전용이라 표시한다.

표면 폐쇄: UF-1은 기준 교정·승인에서 끝나고 지원서 처리 목록으로 이어진다. UF-2는 처리 목록에서 근거 검토와 이견 비교로 이어진다. UF-3는 핸드오프에서 면접 검증·최종 결정과 감사 기록으로 끝난다.

### 역할·행동 경계

| 행동 | HR | HM | LEAD |
|---|---|---|---|
| 기준 교정 표본 입력 | 자신의 기록 생성·수정 | 자신의 기록 생성·수정 | 읽기 |
| 기준 충돌 해결·승인 | 수행 | 읽기 | 읽기 |
| 1차 스크리닝 | 자신의 `ReviewLog` 생성 | 읽기 | 읽기 |
| 직무 서류 검토 | 읽기 | 자신의 `ReviewLog` 생성 | 읽기 |
| 공식 핸드오프 생성 | 읽기 | 읽기 | 수행 |
| 질문 후보 수정·soft delete | 수행 | 수행 | 읽기 |
| 질문 후보 선택 | 읽기 | 읽기 | 수행 |
| 면접 검증·최종 결정 | 읽기 | 읽기 | 수행 |

모든 역할은 다른 검토자의 `ReviewLog`를 수정할 수 없다. 숨김 처리된 제어가 아니라 API 권한 응답을 기준으로 읽기·편집 상태를 결정한다.

## Voice and Tone

마이크로카피는 관찰 가능한 사실, 현재 상태, 다음 행동을 말한다. AI가 판단 주체인 것처럼 쓰지 않는다.

| Do | Don't |
|---|---|
| `기준 v1.2가 승인되었습니다.` | `AI 검증이 완료되었습니다.` |
| `원문 위치를 찾지 못해 문맥으로 표시합니다.` | `근거 확인 실패` |
| `HR과 HM의 판단이 다릅니다. 두 근거를 확인하세요.` | `의견을 통합할까요?` |
| `공식 핸드오프를 만들려면 열린 충돌 2건을 해결하세요.` | `생성할 수 없습니다.` |
| `검토자는 후보를 수정·삭제하고, 현업 리더는 사용할 질문을 선택합니다.` | `AI가 추천한 최적 질문입니다.` |
| `최종 결정은 사람이 입력합니다.` | `합격 가능성이 높습니다.` |

## Evidence & Decision Safety

- 원문 인용구는 AI 요약보다 먼저 보이며 페이지·문단·문맥 중 가용 위치를 함께 표시한다.
- 좌표가 없다는 사실은 근거 부재와 구분한다. 좌표 실패 시 `document-viewer`가 스니펫·페이지·주변 문맥 fallback을 제공한다.
- 승인 전 결과에는 모든 관련 표면에 `미리보기`를 표시하고 `gate-banner`가 공식 핸드오프 차단 이유를 설명한다.
- HR·HM 의견은 `reviewer-comparison`에서 독립 기록으로 유지한다. 시스템은 합치거나 평균내지 않는다.
- 자동 합격·탈락, 자동 필터, 종합 점수, 순위, 보호 특성에 근거한 질문을 제공하지 않는다.
- `question-candidate`는 질문 이유, 연결 기준, 참조 근거를 항상 함께 보여준다. 선택되지 않은 질문은 최종 질문으로 표시하지 않는다.
- 삭제·재처리·재시도는 과거 기록을 덮어쓰지 않고 `audit-timeline`에 새 이벤트로 남긴다.

## Component Patterns

시각 규격은 `DESIGN.md.Components`에 있다.

| 컴포넌트 | 사용 | 행동 규칙 |
|---|---|---|
| `workflow-nav` | 전역 | 완료·현재·잠김 단계를 텍스트로 표시한다. 잠긴 단계 선택 시 선행 조건으로 이동한다. |
| `context-bar` | 전역 | 포지션·기준 버전·승인 상태·역할을 유지한다. 컨텍스트 변경 전 미저장 입력을 경고한다. |
| `status-badge` | 전역 | 상태명과 아이콘을 함께 노출하고 보조 설명을 접근 가능한 이름에 포함한다. |
| `gate-banner` | 교정, 검토, 핸드오프 | 차단 이유, 남은 조건, 이동 가능한 다음 행동을 제공한다. 단순 비활성 버튼을 대체한다. |
| `calibration-matrix` | 기준 교정·승인 | HR·HM이 독립 입력한다. 충돌 행을 열면 양쪽 근거와 해결 사유 입력으로 이동한다. |
| `application-row` | 지원서 처리 목록 | 행 전체로 지원서를 연다. 완료 전 행은 상태 상세만 열고 공식 검토로 이동하지 않는다. |
| `processing-stepper` | 지원서 행 상세 | 마지막 성공 단계, 현재 단계, 실패 이유를 보존한다. 재시도 API는 미정이므로 버튼을 임의 제공하지 않는다. |
| `evidence-split-view` | 근거 검토 | 두 패널을 독립 스크롤한다. 선택된 `active_citation_id`를 양쪽에 동기화한다. |
| `document-viewer` | 근거 검토 | 인용구 선택 시 해당 위치로 이동한다. 좌표 부재 시 스니펫·페이지·문맥 박스로 전환한다. |
| `evidence-card` | 근거 검토 | 기준·인용구·위치를 한 단위로 선택한다. `근거 없음`도 명시적 상태로 유지한다. |
| `review-control` | 근거 검토 | Architecture의 `FULFILLED/PARTIALLY_FULFILLED/UNFULFILLED/UNVERIFIABLE`를 각각 `충족/부분 충족/미충족/확인 불가`로 표시하고 판단 사유를 저장한다. |
| `reviewer-comparison` | 이견 비교, 핸드오프 | HR·HM 열을 독립적으로 유지한다. 다른 사람의 `ReviewLog`는 읽기 전용이다. |
| `handoff-card` | 핸드오프 | 승인 기준·처리 완료·근거·검토 로그가 모두 있을 때 LEAD만 공식 생성을 확정한다. 생성 요청과 결과는 하나의 서버 트랜잭션으로 취급한다. |
| `question-candidate` | 핸드오프 | 핸드오프 생성 시 서버가 후보를 만들고 원문 질문과 현재 수정본을 구분한다. HR·HM 검토자는 수정·soft delete, LEAD는 선택만 수행하며 선택 후보만 최종 핸드오프에 포함한다. |
| `verification-comparison` | 면접 검증·최종 결정 | 서류 가설과 면접 결과를 분리 입력한다. 최종 결정은 별도 명시적 저장으로 확정한다. |
| `audit-timeline` | 감사 기록 | 최신순/시간순 전환, 행위자·시각·버전·참조 근거 열기를 제공한다. 과거 이벤트는 편집하지 않는다. |
| `button-primary` | 전역 | 한 표면의 단일 우선 행동. 처리 중 중복 제출을 막고 완료/실패를 알린다. |
| `field-control` | 폼 전역 | 항상 보이는 레이블, 도움말, 인라인 오류를 제공한다. 오류 후 입력값과 포커스를 보존한다. |
| `loading-skeleton` | 전역 cold-load | 실제 표면 구조만 예고한다. 기존 상태를 추정해 표시하지 않으며 로드가 끝나면 같은 위치의 실제 콘텐츠로 교체한다. |
| `tab-switcher` | 근거 검토, 이견 비교 | 방향키로 탭을 이동하고 활성 탭만 패널에 연결한다. 탭 전환 후 `active_citation_id`와 미저장 판단을 보존한다. |
| `overlay-surface` | 전역 보조 작업 | 드롭다운·팝오버·짧은 편집에 사용한다. `Esc`로 닫고 호출 요소에 포커스를 돌리며 중첩은 한 단계까지만 허용한다. |
| `confirmation-dialog` | 승인·생성·삭제·결정 | 대상 버전/리소스와 저장 결과를 명시한다. 취소가 기본 안전 행동이며 확인 중 중복 제출을 막는다. |
| `error-summary` | 모든 편집 표면 | 오류 수와 필드 링크를 제공하고 첫 오류로 포커스를 이동한다. 인라인 오류와 입력값을 함께 보존한다. |
| `live-region` | 전역 비동기 결과 | 처리 단계와 저장·승인·생성·결정 결과를 `polite`로 알린다. 즉시 대응이 필요한 저장 실패만 `assertive`를 사용한다. |

## State Patterns

| 상태 | 표면 | 처리 |
|---|---|---|
| 초기 로딩 | 전역 | `loading-skeleton`을 실제 레이아웃과 맞춘다. 기존 승인·검토 상태를 추정해 먼저 표시하지 않는다. |
| 기준 `DRAFT` | 교정 | `미리보기`와 `OPEN` 충돌 수를 표시한다. 승인 전 공식 핸드오프·최종 결정은 `gate-banner`로 차단한다. |
| 기준 `APPROVED` | 전역 | 버전 ID와 승인 시각을 고정 표시한다. 기존 버전 편집 대신 새 버전을 만들 필요가 있음을 알린다. |
| 기준 `ARCHIVED` | 교정/감사 기록 | `보관됨 · 읽기 전용`으로 표시한다. 기존 기록은 열람할 수 있지만 새 검토·핸드오프·결정에는 선택할 수 없다. |
| 검토 `FULFILLED` | 근거 검토/이견 비교 | `충족` 레이블, 검토자, 판단 사유, 참조 근거를 함께 표시한다. 자동 합격 의미를 부여하지 않는다. |
| 검토 `PARTIALLY_FULFILLED` | 근거 검토/이견 비교 | `부분 충족` 레이블과 충족·부족 근거를 함께 표시하고 추가 검증 지점을 남긴다. |
| 검토 `UNFULFILLED` | 근거 검토/이견 비교 | `미충족` 레이블과 원문 기반 사유를 표시한다. 자동 탈락 행동은 제공하지 않는다. |
| 검토 `UNVERIFIABLE` | 근거 검토/이견 비교 | `확인 불가` 레이블과 근거 부재 또는 문서 한계를 표시하고 인터뷰 검증 대상으로 연결할 수 있다. |
| 충돌 `OPEN` | 교정/이견 비교 | 양쪽 판단·근거와 충돌 사유를 모두 표시한다. 승인 차단과 해결 사유 입력을 제공하고 한쪽을 자동 선택하지 않는다. |
| 충돌 `RESOLVED` | 교정/이견 비교/감사 기록 | `해결됨`과 해결자·시각·사유를 읽기 전용으로 표시한다. 원래 두 판단과 근거는 계속 열람 가능하다. |
| 지원서 없음 | 처리 목록 | PDF 요구와 합성 데이터 원칙을 설명하고 업로드 진입점을 제공한다. |
| 처리 `RECEIVED` | 처리 목록 | `수신됨`과 업로드 시각을 표시한다. 검토 진입은 막고 다음 서버 단계를 기다린다. |
| 처리 `PARSING` | 처리 목록 | `PDF 분석 중`과 LlamaParse 단계를 표시한다. 원본 PDF 연결은 유지하되 근거 결과는 아직 노출하지 않는다. |
| 처리 `MAPPING` | 처리 목록 | `기준별 근거 연결 중`과 승인 기준 버전을 표시한다. 부분 결과를 완료 결과처럼 열지 않는다. |
| 처리 `COMPLETED` | 처리 목록/근거 검토 | `처리 완료`와 완료 시각·기준 버전을 표시하고 근거 검토 진입을 허용한다. |
| 처리 `FAILED` | 처리 목록/검토 | 실패 단계·사유·이전 성공 산출물을 표시한다. 임의 재시도 행동은 제공하지 않는다. |
| 근거 없음 | 근거 검토 | `원문에서 확인 가능한 근거가 없습니다.`를 기준별로 표시한다. 빈칸으로 두지 않는다. |
| 좌표 없음 | 근거 검토 | 실패가 아닌 `문맥 보기` 상태로 스니펫·페이지·주변 문맥을 표시한다. |
| 두 번째 검토 없음 | 이견 비교 | 제출된 검토와 `아직 검토하지 않음`을 분리 표시한다. |
| 핸드오프 로딩/empty | 핸드오프 | `loading-skeleton` 후 아직 카드가 없으면 생성 전제와 LEAD용 생성 행동을 표시한다. |
| 핸드오프 생성 불가 | 핸드오프 | 미승인 기준, 미완료 처리, 누락 근거·검토 로그를 각각 표시하고 해당 표면으로 가는 링크를 제공한다. |
| 핸드오프 생성 중 | 핸드오프 | LEAD의 중복 요청을 막고 대상 지원서·기준 버전을 고정한다. `live-region`으로 진행 상태를 알린다. |
| 핸드오프 생성 완료 | 핸드오프/감사 기록 | 서버가 반환한 카드 ID, 기준 버전, 생성 시각과 질문 후보를 표시한다. 생성 전 입력과 연결은 읽기 전용으로 보존한다. |
| 핸드오프 stale/conflict | 핸드오프 | 생성 직전 서버 상태가 바뀌면 성공으로 추정하지 않는다. 최신 전제와 기존 화면의 차이를 보여주고 재조회한다. |
| 핸드오프 생성 실패 | 핸드오프 | 입력과 현재 문맥을 보존하고 서버 오류를 표시한다. 생성 성공 레코드가 없으면 카드나 질문 후보를 임의로 만들지 않는다. |

| 질문 `SELECTED` | 핸드오프/면접 검증 | `최종 질문으로 선택됨`을 체크+텍스트로 표시한다. LEAD의 선택 결과만 최종 목록에 포함한다. |
| 질문 `DELETED` | 핸드오프/감사 기록 | 기본 후보 목록에서는 숨기고 감사 기록에서 `삭제됨`과 원문·수정본·행위자를 읽기 전용으로 보존한다. 선택할 수 없다. |
| 질문 생성 실패/없음 | 핸드오프 | 질문을 사실처럼 생성하지 않는다. 실패 이유와 수동 질문 입력 가능 여부는 API 계약 전까지 유보한다. |
| 면접 전 | 면접 검증 | 서류 가설은 읽기 전용, 검증 결과는 빈 명시 상태로 표시한다. |

| 최종 결정 stale/conflict | 면접 검증·최종 결정 | 서버의 최신 핸드오프 상태를 다시 보여주고 입력값은 보존한다. 사용자가 차이를 확인하기 전 재제출하지 않는다. |
| 감사 기록 empty | 감사 기록 | `아직 기록된 이벤트가 없습니다.`와 현재 필터 범위를 표시한다. 가짜 예시 이벤트를 넣지 않는다. |
| 감사 기록 filter-empty | 감사 기록 | 전체 이벤트 수와 `현재 필터에 결과 없음`을 구분하고 필터 초기화를 제공한다. |
| 감사 기록 load-error | 감사 기록 | 이전에 읽은 이벤트를 최신으로 가장하지 않는다. 오류와 재조회 행동을 표시하되 이벤트를 수정하지 않는다. |
| 저장 실패 | 모든 편집 표면 | 입력을 보존하고 `error-summary`와 해당 필드 오류를 함께 표시한다. |
| 권한 없음 | 모든 표면 | 읽기 가능 범위와 필요한 역할을 설명한다. 숨겨진 편집 제어를 키보드 포커스에 남기지 않는다. |
| 오프라인 | 전역 | 상단 상태를 표시하고 모든 서버 쓰기를 차단한다. 자동 성공처럼 보이지 않는다. |

## Interaction Primitives

- 기본 조작은 포인터와 키보드에 동등하게 제공한다. `Tab`은 시각적 읽기 순서를 따르고 `Enter/Space`로 행·카드·선택을 실행한다.
- `Esc`는 현재 `overlay-surface`를 닫고 호출 요소로 포커스를 돌린다. `confirmation-dialog`가 열려 있으면 먼저 안전한 취소 경로를 제공하고 중첩은 한 단계까지만 허용한다.
- `evidence-card` 선택 후 포커스는 카드에 남고 `document-viewer` 위치 변경은 `aria-live="polite"`로 알린다.
- 스플릿 패널의 스크롤은 독립적이지만 선택된 근거 관계는 유지한다. 문서 위치 변경으로 판단 입력을 잃지 않는다.
- 파괴적 행동과 공식 승인·생성·최종 결정은 `confirmation-dialog`에 대상 버전과 결과를 명시한다.
- **금지:** drag-only 조작, hover-only 행동, 무한 스크롤, 색만으로 선택 표시, 자동 다음 단계 이동, AI 자동 결론 애니메이션.

## Accessibility Floor

[ASSUMPTION] MVP 접근성 바닥은 WCAG 2.2 AA다.

- 일반 본문 대비 4.5:1, 큰 텍스트와 비텍스트 UI 3:1 이상을 유지한다. `{colors.primary}`/흰색은 5.33:1이다.
- 모든 상태는 텍스트+아이콘으로 중복 부호화한다. 검토자와 근거 관계를 위치나 색만으로 전달하지 않는다.
- 200% 확대에서 가로 페이지 스크롤 없이 주요 흐름을 수행한다. 데이터 표는 자체 가로 스크롤과 고정 행 레이블을 제공한다.
- PDF 좌표 하이라이트에는 같은 내용을 담은 텍스트 스니펫·페이지·문맥 대체가 항상 존재한다.
- `reviewer-comparison`의 시각적 열 순서는 DOM 읽기 순서와 같다. 각 열 시작에 검토자 이름·역할을 다시 읽는다.
- `error-summary`는 첫 오류로 이동하며, 저장·승인·생성 결과는 `live-region`으로 알린다.
- 모든 목표 크기는 최소 44×44 CSS px다. focus ring은 지우지 않는다.
- 모션 감소 설정에서 스크롤 이동은 즉시 전환하고 상태 애니메이션을 제거한다.

## Inspiration & Anti-patterns

- **Code.Presso에서 차용:** Pretendard, 선명한 블루와 네이비, 깨끗한 흰/옅은 블루 표면, 절제된 라운딩, 복잡한 기술 정보를 카드로 정돈하는 태도.
- **제품에 맞게 변형:** 마케팅용 대형 영웅 이미지와 광택 효과 대신 원문·기준·판단의 조밀한 업무 위계를 사용한다.
- **거부 — ATS 랭킹 대시보드:** 점수, 순위, 합격 확률은 비목표와 충돌하고 사람의 판단을 왜곡한다.
- **거부 — AI 단일 요약:** 원문 근거와 검토자 이견을 숨기므로 사용하지 않는다.
- **거부 — 초록=합격/빨강=탈락:** 검토 상태를 채용 결과처럼 오해하게 하므로 텍스트·아이콘·근거를 우선한다.

## Key Flows

### UF-0 PDF 지원서 입력과 처리 — 민지, 채용 담당자

1. 민지는 승인된 기준 버전이 표시된 지원서 처리 목록을 연다.
2. PDF만 허용하는 업로드 `field-control`에서 비식별 또는 합성 지원서를 선택한다.
3. 파일명·형식·대상 포지션·기준 버전을 확인하고 업로드를 제출한다.
4. `application-row`와 `processing-stepper`가 `RECEIVED → PARSING → MAPPING`을 서버 상태대로 표시한다.
5. 처리 중에는 부분 근거를 열 수 없고, 민지는 다른 행을 확인한 뒤 같은 목록으로 돌아올 수 있다.
6. **Climax:** 상태가 `COMPLETED`로 바뀌고 기준 버전과 완료 시각이 고정되며 근거 검토 진입이 열린다.

실패 경로: PDF가 아니면 제출 전에 형식 오류를 표시한다. 파싱·매핑 실패 시 `FAILED` 단계·사유·마지막 성공 산출물을 보존하고, API 계약이 없는 재시도 버튼을 임의로 만들지 않는다.

### UF-1 기준 합의와 검토 시작 — 민지, 채용 담당자

1. 민지는 기준 교정·승인 표면에서 B2B 영업 매니저 포지션과 기준 버전을 확인한다.
2. `calibration-matrix`에서 자신의 표본 상태와 원문 위치를 입력한다.
3. 준호의 독립 입력이 도착하면 열린 충돌 행을 확인한다.
4. 각 행에서 두 근거와 충돌 사유를 읽고 해결 사유를 기록한다.
5. 열린 충돌이 0건이 되면 기준 승인 확인에서 버전과 결과를 재확인한다.
6. **Climax:** 승인 후 `context-bar`에 고유 기준 버전 ID와 `승인됨`이 고정되고 지원서 처리 단계가 열린다.

실패 경로: 충돌이 남아 있으면 `gate-banner`가 승인 버튼 대신 남은 행과 이동 링크를 보여준다. 서버 승인 실패 시 입력을 보존하고 해당 버전 상태를 다시 조회한다.

### UF-2 근거 기반 지원서 검토 — 준호, HM

1. 준호는 완료 상태의 대표 지원서를 선택한다.
2. `evidence-split-view`에서 왼쪽 원문과 오른쪽 기준별 `evidence-card`를 본다.
3. 선택한 B2B 영업 기준의 인용구를 선택해 원문 위치와 주변 문맥을 확인한다.
4. 좌표가 없는 근거는 `document-viewer`의 스니펫·페이지·문맥 fallback으로 확인한다.
5. `review-control`에서 상태와 원문 기반 판단 사유를 저장한다.
6. 이견 비교에서 민지의 판단과 자신의 판단·근거가 분리되어 있음을 확인한다.
7. **Climax:** 저장된 판단이 승인 기준 버전과 연결되고, 이견이 사라지지 않은 채 핸드오프 준비 상태로 표시된다.

실패 경로: 파싱·매핑이 실패한 지원서는 완료처럼 열리지 않는다. 저장 실패 시 판단 입력과 선택 근거를 유지하고 재시도를 안내한다.

### UF-3 현업 핸드오프와 인터뷰 검증 — 서연, 현업 리더

1. 서연은 핸드오프 표면에서 적용 기준, 원문 근거, HR·HM 판단, 열린 우려를 한 화면에서 확인한다.
2. 공식 생성 조건을 확인하고 LEAD 권한으로 핸드오프 생성을 확정한다.
3. 생성된 `handoff-card`와 각 `question-candidate`의 이유, 연결 기준, 참조 근거, 원문/현재 수정본을 읽는다.
4. HR·HM 검토자가 수정·soft delete한 후보 이력을 확인하고, LEAD 권한으로 인터뷰에 사용할 후보만 선택한다.
5. 인터뷰 후 `verification-comparison`에 실제 검증 결과를 입력한다.
6. 서류 단계 가설과 결과를 비교한 뒤 최종 결정과 사람의 사유를 저장한다.
7. **Climax:** `audit-timeline`에 승인 기준, 원문 근거, 세 역할의 기록, 선택 질문, 면접 결과, 최종 결정이 하나의 재현 가능한 흐름으로 남는다.

실패 경로: 기준이 미승인되었거나 처리가 완료되지 않았으면 공식 핸드오프를 만들지 않고 충족되지 않은 전제로 이동한다. 질문 생성 실패가 자동 질문이나 결론으로 대체되지 않는다.

## Open Decisions

- D-01 질문 후보의 정확한 개수.
- D-02 발표 데이터 세트의 정확한 수량과 구성.
- D-07 좌표 하이라이트 지원 범위.
- 새 기준 버전, 지원서 충돌 해결, 처리 재시도, PDF 스트리밍 API 계약.
- 모바일에서 공식 승인·최종 결정을 허용할지 여부.

이 항목들은 구현 전 확정 대상이며, 현재 초안이 임의로 API나 데이터 의미를 확정하지 않는다.
