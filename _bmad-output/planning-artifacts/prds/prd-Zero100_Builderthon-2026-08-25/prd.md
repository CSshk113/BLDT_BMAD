# 근거 기반 채용 핸드오프 시스템 PRD

## 1. 제품 요약

Code.presso가 5일 안에 검증할 B2B 채용 보조 MVP다. 대량 지원서 검토에서 발생하는 시간 부족과 서류-현업 간 연결 단절을 줄인다. 제품은 자동 합격·탈락을 결정하지 않고, 합의된 평가 기준을 적용해 원문 근거를 매핑하고 사람의 판단 사유를 핸드오프 가능한 기록으로 남긴다.

## 2. 문제와 기회

채용 담당자는 많은 지원서를 빠르게 검토해야 하지만, 직무 기준을 지원서 원문과 연결해 확인하는 데 시간이 든다. 직무 담당자와 판단 기준이 다르게 해석되면 재검토가 발생하고, 최종적으로 왜 특정 판단을 했는지가 Slack 등 분산된 대화에 남는다.

이 MVP의 기회는 AI가 판단을 대체하는 것이 아니라, 검토자가 같은 기준과 같은 원문을 보고 더 빠르고 재현 가능하게 판단하도록 돕는 데 있다.

## 3. 목표와 비목표

### 목표

- 대량 검토 전에 채용 담당자와 직무 담당자가 평가 기준과 허용 근거를 합의하고 버전을 고정한다.
- 지원서별 평가 기준과 원문 인용구·페이지·문단 위치를 연결해 검토자가 빠르게 근거를 확인할 수 있게 한다.
- 1차 판단, 의견 차이, 미검증 질문, 인터뷰 검증 질문 후보를 핸드오프 카드로 전달하고 결정 사유를 축적한다.
- 5일 안에 핵심 흐름을 해커톤 심사·발표용 데모로 완성한다.
- 짧은 발표 안에 “기준 합의 → 원문 근거 확인 → 판단 사유 핸드오프”의 차별적 흐름을 재현한다.
- 5분 발표와 5분 질의응답 안에 문제의 크기, 신뢰 설계, 차별성, 실행 가능성을 전달한다.

### 우선순위와 의존성

- **Priority 1 — F3 공동 판단 로그와 현업 핸드오프 카드:** 발표의 핵심 출력이자 사용자가 직접 가치를 확인하는 기능
- **Priority 2 — F1 기준 교정 게이트:** 공식 판단과 핸드오프를 신뢰할 수 있게 하는 선행 조건
- **Priority 3 — F2 근거 매핑형 자격 대조기:** 핸드오프에 들어갈 근거를 제공하는 지원 기능

우선순위와 실제 동작 의존성은 다르다. 구현 흐름은 `F1 기준 승인 → F2 근거 확인 → F3 핸드오프 생성` 순서를 따른다.

### 비목표 및 가드레일

- 자동 합격·탈락 결정 또는 그 결과에 따른 자동 필터링
- 종합 점수, 순위, 자동 랭킹
- AI의 검토자 의견 통합·중재
- 승인되지 않은 기준 버전으로 평가 파이프라인 실행
- 채용 공고 게시, 지원자 유입, ATS 전체 대체

## 4. 사용자와 역할

- **채용 담당자:** 평가 기준을 정리하고 직무 담당자와 교정·승인을 진행한다.
- **직무 담당자:** 직무 기준의 의미와 원문으로 인정할 근거를 검토하고 후보자 판단을 남긴다.
- **현업 리더:** 핸드오프 카드를 읽고 인터뷰 검증 질문과 최종 판단에 활용한다.

[ASSUMPTION A-01] 5일 해커톤 데모에서는 하나의 채용 포지션과 제한된 협업 팀을 대상으로 하며, 권한 체계는 역할별 최소 구분만 제공한다.

[ASSUMPTION A-02] 시연 포지션은 백엔드 개발자로 한다. 필수 기준은 Python, REST API 개발 경험, 실제 서비스 배포 경험으로 시작하고, 우대 기준은 Docker·SQL 경험으로 한다. 이 선택은 시장 대표성이 아니라 화면과 근거 매핑을 설명하기 쉬운 예시라는 이유로 채택한다.

## 5. 핵심 유저 플로우

### UF-1 기준 합의와 검토 시작

가상의 주인공 민지(채용 담당자)와 준호(직무 담당자)는 동일한 기준 버전과 교정용 표본을 확인한다. 각자 4가지 검토 상태와 원문 위치를 기록하고, 불일치 항목의 충돌 사유를 확인한다. 미승인 기준으로도 민지는 탐색용 미리보기를 시작할 수 있지만, 공식 핸드오프 카드 생성은 승인 전까지 차단된다. 합의가 완료되면 기준 버전에 고유 ID가 발급된다.

### UF-2 근거 기반 지원서 검토

준호(직무 담당자)는 지원서 원문과 기준 패널이 함께 있는 스플릿 뷰에서 기준별 매칭 근거를 확인한다. 인용구를 선택하면 정확한 원문 스니펫, 페이지 또는 문서 위치와 주변 문맥을 확인한다. 좌표 기반 하이라이트가 가능한 경우 원문 위치를 강조하고, 실패하면 스니펫·페이지·문맥 박스로 대체한다. 준호는 원문에 기반한 상태와 판단 사유를 남긴다.

### UF-3 현업 핸드오프와 인터뷰 검증

가상의 주인공 서연(현업 리더)은 핸드오프 카드에서 지원서 원문, 기준, 1차 판단 근거, 의견 차이, 미검증 질문, 인터뷰 검증 질문 후보를 한 화면에서 확인한다. 질문 후보는 근거가 부족하거나 확인이 필요한 기준에 연결된다. 서연은 질문을 수정·선택해 인터뷰에 사용하고, 인터뷰 후 결과를 입력해 서류 단계의 우려·가설과 실제 검증 결과를 비교 기록한다.

## 6. 기능 요구사항

### F1. 기준 교정 게이트 — Priority 2: 공식 판단의 선행 조건

**FR-001** 시스템은 포지션별 평가 기준을 기준 버전 단위로 관리해야 한다.

**FR-002** 시스템은 교정용 표본에서 두 검토자가 기준별 검토 상태와 원문 위치를 독립적으로 입력할 수 있게 해야 한다. [ASSUMPTION A-03] 데모의 4가지 상태명은 `충족`, `부분 충족`, `미충족`, `확인 불가`로 시작한다.

**FR-003** 시스템은 두 검토자의 상태·원문 위치가 다를 때 불일치 항목과 충돌 사유를 표시해야 한다.

**FR-004** 미해결 충돌이 있는 기준 버전은 미승인 상태로 유지되어야 한다. 미승인 버전의 탐색용 검토 결과는 생성할 수 있지만 `미리보기`로 표시해야 하며, 공식 핸드오프 카드 생성은 차단해야 한다.

**FR-005** 기준 버전이 승인되면 고유 버전 ID를 발급하고, 이후 생성되는 모든 검토 카드와 핸드오프 카드가 해당 ID를 참조해야 한다.

### F2. 근거 매핑형 자격 대조기 — Priority 3: 핸드오프 근거 지원

**FR-006** 시스템은 지원서의 기준별 매핑 결과에 원문 텍스트 인용구를 연결해야 한다.

**FR-007** 각 인용구는 LlamaParse 변환 Markdown의 문단·헤딩·페이지 정보 또는 원본 PDF에서 확인 가능한 위치를 가져야 한다. 좌표를 안정적으로 얻을 수 없는 문서는 스니펫, 페이지, 주변 문맥을 위치 정보의 대체 표현으로 제공해야 한다.

**FR-008** 매핑 결과는 AI가 새로 작성한 요약문이 아니라 검토 가능한 원문 근거를 우선 표시해야 한다.

**FR-009** 검토 화면은 좌측 원문 뷰어와 우측 기준 패널의 스플릿 뷰를 제공해야 한다.

**FR-010** 우측 기준 패널의 인용구를 선택하면 원문 스니펫과 위치 정보가 즉시 표시되어야 한다. 좌표 기반 원문 포커싱·하이라이트는 지원 가능한 문서에서 제공하며, 실패 시 스니펫·페이지·주변 문맥 표시로 자동 대체해야 한다.

**FR-011** 시스템은 승인된 기준 버전 없이 공식 핸드오프 및 최종 판단 기록을 생성하지 않아야 한다. 미승인 기준의 탐색용 결과에는 `미리보기`와 기준 상태를 명시해야 한다.

**FR-012** 시스템은 PDF 지원서를 입력으로 받고, LlamaParse를 통해 Markdown으로 변환한 뒤 승인된 기준 버전에 따라 입력·처리·출력할 수 있어야 한다. PDF 원본과 변환된 Markdown은 동일 지원서의 근거로 연결되어야 한다.

**FR-012a** 200건 처리 요구는 발표 당일 실시간 처리량이 아니라 향후 확장 목표로 기록하며, 데모에서는 사전 처리 또는 고정된 데모 데이터를 사용할 수 있다.

**FR-012b** 시스템은 PDF 원본, LlamaParse 변환 Markdown, 기준별 인용구와 위치 정보를 한 지원서 단위로 추적할 수 있어야 한다. 변환 또는 위치 추출에 실패하면 처리 상태와 실패 사유를 표시하고 스니펫·페이지·주변 문맥 fallback을 제공해야 한다.

### F3. 공동 판단 로그와 현업 핸드오프 카드 — Priority 1: 핵심 발표 출력

**FR-013** 검토자는 지원서별 판단 상태와 원문에 기반한 판단 사유를 저장할 수 있어야 한다.

**FR-014** 핸드오프 카드는 지원서 원문, 적용 기준, 1차 판단 근거, 미검증 질문, 인터뷰 검증 질문 후보를 한 화면에 제공해야 한다.

**FR-015** 두 담당자의 의견 차이와 각자가 참조한 근거를 분리해 표시해야 한다.

**FR-016** 현업 리더는 핸드오프 카드를 열람하고 인터뷰 검증 질문을 확인할 수 있어야 한다.

**FR-017** 인터뷰 완료 후 최종 결과를 입력하고, 서류 단계의 초기 가설과 면접 검증 결과를 비교 기록할 수 있어야 한다.

**FR-018** 결정 로그는 기준 버전 ID와 연결되어야 하며, 사후에 어떤 기준과 근거로 판단했는지 재현할 수 있어야 한다.

**FR-019** 시스템은 핸드오프 카드의 적용 기준, 근거가 부족한 항목, 검토자가 남긴 우려 지점을 바탕으로 인터뷰 검증 질문 후보를 여러 개 생성해야 한다. 정확한 질문 개수는 [DEFERRED D-01]로 남기고 구현 전에 확정한다.

**FR-020** 각 인터뷰 검증 질문 후보는 확인하려는 기준 또는 우려 지점과 연결되어야 하며, 질문이 필요한 이유와 참조 근거를 함께 표시해야 한다.

**FR-021** 검토자는 생성된 질문 후보를 수정·삭제·선택할 수 있어야 하며, 시스템은 선택되지 않은 질문을 최종 인터뷰 질문으로 표시하지 않아야 한다.

**FR-022** 인터뷰 검증 질문은 지원자의 합격·탈락을 자동 결정하거나 새로운 사실을 단정하는 문장이 아니라, 서류에서 확인되지 않은 내용을 검증하기 위한 질문이어야 한다.

### 인터뷰 검증 질문 품질 기준 — MVP 기본값

생성된 질문 후보는 다음 기준을 모두 만족해야 한다.

- **근거 연결:** 질문이 어떤 평가 기준, 근거 부족 항목 또는 검토자의 우려에서 나왔는지 표시한다.
- **검증 가능성:** 인터뷰 답변으로 해당 기준 충족 여부나 우려를 확인·반박할 수 있어야 한다.
- **구체성:** “자기소개해 주세요” 같은 일반 질문이 아니라 특정 경험·행동·상황을 묻는다.
- **비유도성·공정성:** 답을 특정 방향으로 유도하지 않으며, 지원자의 사생활이나 보호 특성을 근거 없이 묻지 않는다.
- **중복 최소화:** 생성된 질문 후보가 같은 내용을 반복하지 않고 서로 다른 미검증 지점을 다룬다.

[DEFERRED D-01] 질문 후보의 정확한 개수는 발표 시연 범위와 화면 밀도를 확인한 뒤 구현 전에 결정한다. 개수와 관계없이 각 질문에 `질문 이유`, `연결된 기준`, `참조 근거`를 함께 표시한다.

## 7. 비기능 요구사항과 품질 기준

- **근거 추적성:** 모든 매핑 근거는 원문 위치로 역추적 가능해야 한다. 위치를 확인할 수 없는 생성 텍스트는 근거로 표시하지 않는다.
- **안전한 실행:** 미승인 기준 버전의 공식 핸드오프와 최종 판단 기록을 차단하고, 탐색용 미리보기에는 기준 상태를 표시한다.
- **검토 속도:** 지원서 1건당 근거 확인과 판단 사유 기록 시간을 기존 방식과 비교해 측정한다. `2분 이내`는 측정 전 확정 목표가 아니라 보조 검증 지표로 둔다.
- **대량 입력:** 발표용 입력 데이터가 확정되면 처리 상태 또는 오류 상태를 사용자에게 보여야 한다. 200건은 후속 확장 목표다.
- **감사 가능성:** 기준 버전, 검토자, 판단 사유, 참조 근거, 변경 시점을 기록해야 한다.
- **데모 데이터 안전:** 발표에서는 비식별 또는 합성 지원서 데이터를 사용한다. 실제 개인정보를 사용하지 않는다.
- **AI 모델 기준:** MVP와 베이스라인은 `gpt-5.6-luna`로 통일한다. 실제 사용 시 프로젝트 계정에서 모델 ID 가용성을 확인하고, 사용 시점의 정확한 API 모델 스냅샷을 고정한다. API 키와 선택 가능한 API base URL은 환경 변수로 관리하며 소스 코드와 저장소에 비밀값을 포함하지 않는다.

[ASSUMPTION A-04] 5일 안에는 다중 테넌시, SSO, 외부 ATS 연동, 운영 수준의 보존 정책, 실제 고객 온보딩을 구현하지 않는다. 발표용 제한 환경에서 핵심 가치만 검증한다.

[DEFERRED D-02] 발표 데이터는 개인정보가 제거된 합성 또는 비식별 PDF로 구성한다. 정확한 파일 수, 대표 지원서 선정 기준, 기준 교정용 표본 수는 구현 전에 결정한다. PDF 입력과 LlamaParse 기반 Markdown 변환은 확정되어 있으며, 실제 지원서와 실명은 사용하지 않는다.

## 8. 성공 지표와 역지표

### 성공 지표

- 대표 검토 흐름에서 지원서 1건당 근거 확인과 판단 사유 기록 시간을 기존 방식과 비교해 측정한다.
- 확정된 발표용 입력 전체가 기준별 근거 매핑 또는 `근거 없음` 상태를 갖는다.
- 검토되지 않은 지원서가 결과 화면에서 조용히 누락되지 않고 처리 상태를 확인할 수 있다.
- 모든 공식 핸드오프 카드가 승인된 기준 버전 ID를 참조한다.
- 두 검토자의 불일치가 사라지지 않고 충돌 항목과 근거로 표시된다.
- 교정 게이트에서 두 검토자의 불일치 항목을 식별하고 승인된 기준 버전을 생성할 수 있다.
- 매핑 결과의 기준별 인용구를 선택하면 스니펫·페이지·주변 문맥이 표시된다. 좌표 기반 하이라이트는 가능한 입력에서만 추가 제공한다.
- 핸드오프 카드만으로 현업 리더가 지원자의 근거, 우려, 인터뷰 질문을 파악할 수 있다.
- 핸드오프 카드에 포함된 인터뷰 검증 질문 후보가 기준 또는 우려 지점과 연결되고, 현업 리더가 질문을 선택·수정할 수 있다.
- 발표 시나리오에서 입력 지원서 묶음이 승인 기준 버전, 매핑 근거, 결정 로그와 누락 없이 연결된다.

### 역지표

- 원문 위치가 존재하지 않거나 인용구와 실제 원문이 불일치하는 매핑 비율
- 승인되지 않은 기준으로 생성된 검토 카드 수
- 자동 랭킹·자동 합격/탈락으로 오해될 수 있는 UI 상호작용 수
- 두 검토자의 충돌이 기록 없이 사라지는 비율
- 핸드오프 카드가 Slack 등 별도 채널의 재작업을 유발하는 비율
- 근거 또는 기준과 연결되지 않은 인터뷰 질문 후보의 비율
- 검토자가 수정·삭제해야 하는 무관하거나 반복적인 질문 후보의 비율

### 필수 제출물

**DEL-001 문제 정의 카드**

병목을 한 문장으로 제시하고, 근거 숫자와 출처, 이번 MVP에서 풀지 않은 것, 성공의 정의를 포함해야 한다. 숫자와 출처는 확정 전까지 임의로 작성하지 않는다.

#### 문제 카드용 근거 후보 — 검증 전

- SHRM 2025 채용 벤치마크는 2,300명 이상의 SHRM 회원 응답을 바탕으로 하며, 56%의 채용 리더가 인재 부족을 문제로 꼽고 비임원·임원 채용의 중간 time-to-fill이 대략 한 달 반이라고 보고한다. 이는 채용 전반의 압박을 보여주는 거시 근거이지, 서류 검토 시간의 직접 근거로 사용하지 않는다. 출처: [SHRM State of Recruiting 2025](https://www.shrm.org/executive-network/insights/people-strategy/state-of-recruiting-2025-insights-to-maximize-recruitment)
- University of Washington의 이력서 가이드는 TheLadders의 시선 추적 연구를 인용해 채용 담당자의 초기 이력서 검토 시간이 평균 6초였다고 설명한다. 다만 연구 표본은 전문 채용 담당자 30명, 10주 관찰이며 미국·과거 연구라는 한계가 있으므로 한국 채용 시장의 대표 통계처럼 말하지 않는다. 출처: [University of Washington Resume Guide](https://hasc.washington.edu/sites/default/files/2023-09/HAS%20Resume%20Guide.pdf), 원 연구가이드 인용: TheLadders.
- 데모 자체의 근거 숫자는 “동일 지원서 묶음에서 범용 LLM과 본 시스템이 원문 위치를 정확히 연결한 비율 및 검토 완료 시간”으로 측정하고, 측정일·입력 수·프롬프트·판정 기준을 함께 기록한다.

**DEL-002 설계 요약 1장**

담당자가 결과를 믿게 만드는 장치와 오판 대응 방식을 설명해야 한다. 승인된 기준 버전, 원문 인용구·위치, 검토자 간 불일치 표시, 인터뷰 질문의 근거 연결과 사람의 수정·선택 절차, 자동 결정 금지 가드레일을 포함한다.

**DEL-003 베이스라인 비교 컷 1장**

동일한 입력을 범용 LLM에 그대로 넣은 결과와 본 제품 결과를 나란히 비교한다. 원문 근거·위치·기준 버전·의견 차이·결정 로그·인터뷰 질문의 근거 연결이 무엇을 다르게 만드는지 한 화면에서 보여줘야 한다. 베이스라인은 사용 시점의 정확한 API 모델 스냅샷, 프롬프트, 입력 자료, 파라미터, 원본 응답, 실행 시각과 요청 ID를 보존해 재현 가능하게 만든다.

#### 베이스라인 비교에 필요한 결정

- **모델:** `gpt-5.6-luna`로 통일한다. 실제 사용 전에 프로젝트 계정에서 해당 모델 ID의 가용성을 확인하고, 사용 시점에 제공되는 정확한 API 모델 스냅샷을 고정한다. 확인되지 않은 모델로 조용히 대체하지 않는다. 참고: [OpenAI 모델 목록](https://developers.openai.com/api/docs/models).
- **비교 사례:** 대표 지원서 5건을 사용한다. 사례는 `명확한 충족`, `부분 충족`, `근거 부족`, `검토자 의견 충돌`, `인터뷰 질문 생성 필요`를 각각 대표해야 한다. 각 사례는 3회 실행해 총 15회 결과를 비교한다.
- **동일 입력:** 페이지 구분이 포함된 지원서 원문, 동일한 승인 기준, 동일한 두 검토자의 판단과 판단 사유를 제공한다.
- **프롬프트:** 제품 내부 데이터 구조나 정답을 제공하지 않고, 일반적인 “근거 기반 핸드오프와 인터뷰 질문 작성” 요청만 제공한다. 실행에 사용한 정확한 프롬프트 문자열은 저장한다.
- **출력 보존:** 모델명·스냅샷, 프롬프트, API 파라미터, 원본 응답, 실행 시각, 요청 ID를 함께 저장해 발표 화면에서 동일한 결과를 재현한다.
- **비교 기준:** 원문 인용 정확성, 페이지·위치 정확성, 근거 없는 추론 수, 확인 불가 처리, 검토자 이견 보존, 인터뷰 질문의 기준·근거 연결, 반복 실행 간 결과 일관성을 평가한다.

**DEL-004 레포지토리 및 배포 링크**

심사자가 데모를 재현하거나 결과를 확인할 수 있도록 저장소 링크와 배포 링크를 제공한다.

### 발표 성공 정의

- 심사자가 1~2분 영상만 보고도 실제 입력부터 근거 기반 출력까지의 흐름을 이해한다.
- 문제 정의 카드가 “왜 필요한가”를 숫자와 출처로 설명한다.
- 설계 요약이 “왜 믿을 수 있는가”와 “오판 시 어떻게 드러나는가”를 설명한다.
- 베이스라인 비교 컷이 범용 LLM과의 차이를 추가 설명 없이 보여준다.
- 발표 시점에 클릭 가능한 데모, 레포, 배포 링크가 모두 접근 가능하다.

## 10. 수상 관점의 제품 포지셔닝

- **비욘드 브리프 상:** 자동 선발이 아니라 기준 교정·근거 매핑·판단 이력이라는 답지 밖의 접근을 선명하게 보여준다.
- **비즈니스 포텐셜 상:** 채용 검토 시간과 서류-현업 핸드오프 비용을 줄이는 B2B 업무 흐름으로 확장 가능성을 설명한다. 시장 규모나 고객 수는 근거 없이 주장하지 않는다.
- **빌더스 초이스 상:** 참가자가 짧은 시간 안에 이해하고 직접 사용해볼 수 있는 직관적인 데모를 우선한다.
- **0→100 상:** 5일 동안 문제 정의에서 실제 입력·처리·출력 데모까지 도달한 성장폭을 증거로 남긴다.

## 11. 발표 시나리오 초안

1. **문제 정의 카드:** 대량 지원서 검토의 병목과 기존 방식의 손실을 한 문장·숫자·출처로 제시한다.
2. **승인된 기준 버전 확인 — 10초:** 기준 버전과 승인 상태를 확인한다.
3. **대표 지원서 선택 — 10초:** 처리 상태 목록에서 대표 지원서를 선택한다.
4. **근거 확인 — 25초:** 인용구를 클릭해 원문 위치를 확인하고, 좌표가 없으면 스니펫·페이지·주변 문맥 fallback을 보여준다.
5. **의견 차이와 핸드오프 — 25초:** 두 검토자의 의견 차이와 근거를 확인한 뒤 핸드오프 카드를 연다.
6. **질문 후보 조정 — 20초:** 인터뷰 질문 후보를 수정·삭제·선택한다.
7. **베이스라인 비교와 마무리:** 같은 입력을 범용 LLM에 넣은 결과와 나란히 비교하고, 자동 합격·탈락을 하지 않는 이유와 레포·배포 링크를 제시한다.

### 13.2 다음 단계 진입 전 Phase-blocker

없음. 기존 아키텍처의 핵심 불일치는 `DEC-04`에 따라 동기화했다. 아키텍처 문서 자체의 별도 finalization은 후속 작업으로 남길 수 있다.

### 13.3 Deferred items — 이후 결정

- **D-01 — 정확한 인터뷰 질문 후보 개수:** 질문 품질 기준과 검토자 선택·수정 흐름은 고정했으며, 정확한 개수만 발표 화면 밀도와 구현 범위를 확인한 후 결정한다. 결정 시점: F3 구현 시작 전.
- **D-02 — 발표용 데이터 세트의 정확한 수량과 구성:** PDF 입력 및 LlamaParse 변환은 고정했지만, 발표용 데이터 세트 자체는 미정으로 유지한다. 이 항목은 PRD finalization과 아키텍처 설계를 막지 않으며, 실제 데모 자산 제작 전에 결정한다.
- **D-03 — 베이스라인 재현 계약(PB-02):** 당분간 실행하지 않는다. 추후 `DEL-003` 제작을 시작할 때 `gpt-5.6-luna` 가용성 확인, 대표 사례 5건 × 3회 실행, 실행 메타데이터 저장, 7개 비교 기준 평가, 대표 비교 화면 생성을 순서대로 진행한다.
- **D-04 — 문제 정의 카드의 최종 근거:** 숫자와 출처는 검증·선정 후 확정한다. 현재 PRD의 외부 자료는 후보와 한계를 기록한 상태이며, 한국 채용 서류 검토의 직접 근거처럼 과장하지 않는다.
- **D-05 — 레포·배포 링크:** 공개 범위와 재현 절차를 결정한다. 결정 시점: 제출 전.
- **D-06 — `2분 이내` 보조 지표 측정:** 비교 기준, 입력 수, 프롬프트, 측정일과 판정 방법을 고정한 뒤 측정한다. 결정 시점: 데모 검증 전.
- **D-07 — PDF 좌표 하이라이트의 지원 범위:** 스니펫·페이지·주변 문맥 fallback은 MVP 필수이고, 좌표 기반 하이라이트는 LlamaParse Markdown의 위치 정보와 입력 문서 특성을 확인한 후 지원 범위를 정한다.

### 13.4 확정된 위험 대응

- PDF·문서 형식별 좌표 추출이 실패하면 원문 스니펫, 페이지, 주변 문맥을 표시한다.
- 원문 인용구는 생성 요약이 아니라 원문과 위치를 함께 저장하고, 샘플링 검수 대상으로 삼는다.
- 미승인 기준은 탐색용 미리보기만 허용하고 공식 핸드오프·최종 판단 기록을 차단한다.
- 인터뷰 질문은 기준·우려·참조 근거를 표시하고, 사람이 수정·삭제·선택한다. 자동 합격·탈락이나 새로운 사실 단정은 금지한다.
