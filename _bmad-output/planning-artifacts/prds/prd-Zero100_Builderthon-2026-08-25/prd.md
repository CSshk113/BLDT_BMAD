# 근거 기반 채용 핸드오프 시스템 PRD

## 1. 제품 요약

Code.presso가 5일 안에 검증할 B2B 채용 보조 MVP다. 대량 지원서 검토에서 발생하는 시간 부족과 서류-현업 간 연결 단절을 줄인다. 제품은 자동 합격·탈락을 결정하지 않고, 합의된 평가 기준을 적용해 원문 근거를 매핑하고 사람의 판단 사유를 핸드오프 가능한 기록으로 남긴다.

## 2. 문제와 기회

채용 담당자는 많은 지원서를 빠르게 검토해야 하지만, 직무 기준을 지원서 원문과 연결해 확인하는 데 시간이 든다. 직무 담당자와 판단 기준이 다르게 해석되면 재검토가 발생하고, 최종적으로 왜 특정 판단을 했는지가 Slack 등 분산된 대화에 남는다.

이 MVP의 기회는 AI가 판단을 대체하는 것이 아니라, 검토자가 같은 기준과 같은 원문을 보고 더 빠르고 재현 가능하게 판단하도록 돕는 데 있다.

## 3. 목표와 비목표

### 목표

- 대량 검토 전에 채용 담당자와 직무 담당자가 평가 기준과 허용 근거를 합의하고 버전을 고정한다.
- 지원서별 평가 기준과 원문 인용구·페이지·문단 위치를 연결해 검토자가 빠르게 근거를 확인할 수 있게 한다.
- 1차 판단, 의견 차이, 미검증 질문을 핸드오프 카드로 전달하고 결정 사유를 축적한다.
- 5일 안에 핵심 흐름을 해커톤 심사·발표용 데모로 완성한다.
- 짧은 발표 안에 “기준 합의 → 원문 근거 확인 → 판단 사유 핸드오프”의 차별적 흐름을 재현한다.
- 5분 발표와 5분 질의응답 안에 문제의 크기, 신뢰 설계, 차별성, 실행 가능성을 전달한다.

### 비목표 및 가드레일

- 자동 합격·탈락 결정 또는 그 결과에 따른 자동 필터링
- 종합 점수, 순위, 자동 랭킹
- AI의 검토자 의견 통합·중재
- 승인되지 않은 기준 버전으로 평가 파이프라인 실행
- 채용 공고 게시, 지원자 유입, ATS 전체 대체

## 4. 사용자와 역할

- **채용 담당자:** 평가 기준을 정리하고 직무 담당자와 교정·승인을 진행한다.
- **직무 담당자:** 직무 기준의 의미와 원문으로 인정할 근거를 검토하고 후보자 판단을 남긴다.
- **현업 리더:** 핸드오프 카드를 읽고 인터뷰 검증 질문과 최종 판단에 활용한다.

[ASSUMPTION] 5일 해커톤 데모에서는 하나의 채용 포지션과 제한된 협업 팀을 대상으로 하며, 권한 체계는 역할별 최소 구분만 제공한다.

[ASSUMPTION] 시연 포지션은 백엔드 개발자로 한다. 필수 기준은 Python, REST API 개발 경험, 실제 서비스 배포 경험으로 시작하고, 우대 기준은 Docker·SQL 경험으로 한다. 이 선택은 시장 대표성이 아니라 화면과 근거 매핑을 설명하기 쉬운 예시라는 이유로 채택한다.

## 5. 핵심 유저 플로우

### UJ-1 기준 합의와 검토 시작

채용 담당자와 직무 담당자는 동일한 기준 버전과 교정용 표본을 확인한다. 각자 4가지 검토 상태와 원문 위치를 기록하고, 불일치 항목의 충돌 사유를 확인한다. 미승인 기준으로도 채용 담당자는 탐색용 미리보기를 시작할 수 있지만, 공식 핸드오프 카드 생성은 승인 전까지 차단된다. 합의가 완료되면 기준 버전에 고유 ID가 발급된다.

### UJ-2 근거 기반 지원서 검토

직무 담당자는 지원서 원문과 기준 패널이 함께 있는 스플릿 뷰에서 기준별 매칭 근거를 확인한다. 인용구를 선택하면 정확한 원문 스니펫, 페이지 또는 문서 위치와 주변 문맥을 확인한다. 좌표 기반 하이라이트가 가능한 경우 원문 위치를 강조하고, 실패하면 스니펫·페이지·문맥 박스로 대체한다. 검토자는 원문에 기반한 상태와 판단 사유를 남긴다.

### UJ-3 현업 핸드오프와 사후 검증

현업 리더는 핸드오프 카드에서 지원서 원문, 기준, 1차 판단 근거, 의견 차이, 미검증 질문을 한 화면에서 확인한다. 인터뷰 후 결과를 입력하고 서류 단계의 우려·가설과 실제 검증 결과를 비교해 기록한다.

## 6. 기능 요구사항

### F1. 기준 교정 게이트

**FR-001** 시스템은 포지션별 평가 기준을 기준 버전 단위로 관리해야 한다.

**FR-002** 시스템은 교정용 표본에서 두 검토자가 기준별 검토 상태와 원문 위치를 독립적으로 입력할 수 있게 해야 한다. [ASSUMPTION] 데모의 4가지 상태명은 `충족`, `부분 충족`, `미충족`, `확인 불가`로 시작한다.

**FR-003** 시스템은 두 검토자의 상태·원문 위치가 다를 때 불일치 항목과 충돌 사유를 표시해야 한다.

**FR-004** 미해결 충돌이 있는 기준 버전은 미승인 상태로 유지되어야 한다. 미승인 버전의 탐색용 검토 결과는 생성할 수 있지만 `미리보기`로 표시해야 하며, 공식 핸드오프 카드 생성은 차단해야 한다.

**FR-005** 기준 버전이 승인되면 고유 버전 ID를 발급하고, 이후 생성되는 모든 검토 카드와 핸드오프 카드가 해당 ID를 참조해야 한다.

### F2. 근거 매핑형 자격 대조기

**FR-006** 시스템은 지원서의 기준별 매핑 결과에 원문 텍스트 인용구를 연결해야 한다.

**FR-007** 각 인용구는 원문 텍스트와 페이지 또는 문서 내 확인 가능한 위치를 가져야 한다. 좌표를 안정적으로 얻을 수 없는 문서는 스니펫, 페이지, 주변 문맥을 위치 정보의 대체 표현으로 제공해야 한다.

**FR-008** 매핑 결과는 AI가 새로 작성한 요약문이 아니라 검토 가능한 원문 근거를 우선 표시해야 한다.

**FR-009** 검토 화면은 좌측 원문 뷰어와 우측 기준 패널의 스플릿 뷰를 제공해야 한다.

**FR-010** 우측 기준 패널의 인용구를 선택하면 원문 스니펫과 위치 정보가 즉시 표시되어야 한다. 좌표 기반 원문 포커싱·하이라이트는 지원 가능한 문서에서 제공하며, 실패 시 스니펫·페이지·주변 문맥 표시로 자동 대체해야 한다.

**FR-011** 시스템은 승인된 기준 버전 없이 공식 핸드오프 및 최종 판단 기록을 생성하지 않아야 한다. 미승인 기준의 탐색용 결과에는 `미리보기`와 기준 상태를 명시해야 한다.

**FR-012** 시스템은 발표 데모에서 합성 비정형 지원서 20건을 입력·처리·출력할 수 있어야 한다.

**FR-012a** 200건 처리 요구는 발표 당일 실시간 처리량이 아니라 향후 확장 목표로 기록하며, 데모에서는 사전 처리 또는 고정된 데모 데이터를 사용할 수 있다.

### F3. 공동 판단 로그와 핸드오프 카드

**FR-013** 검토자는 지원서별 판단 상태와 원문에 기반한 판단 사유를 저장할 수 있어야 한다.

**FR-014** 핸드오프 카드는 지원서 원문, 적용 기준, 1차 판단 근거, 미검증 질문을 한 화면에 제공해야 한다.

**FR-015** 두 담당자의 의견 차이와 각자가 참조한 근거를 분리해 표시해야 한다.

**FR-016** 현업 리더는 핸드오프 카드를 열람하고 인터뷰 검증 질문을 확인할 수 있어야 한다.

**FR-017** 인터뷰 완료 후 최종 결과를 입력하고, 서류 단계의 초기 가설과 면접 검증 결과를 비교 기록할 수 있어야 한다.

**FR-018** 결정 로그는 기준 버전 ID와 연결되어야 하며, 사후에 어떤 기준과 근거로 판단했는지 재현할 수 있어야 한다.

## 7. 비기능 요구사항과 품질 기준

- **근거 추적성:** 모든 매핑 근거는 원문 위치로 역추적 가능해야 한다. 위치를 확인할 수 없는 생성 텍스트는 근거로 표시하지 않는다.
- **안전한 실행:** 미승인 기준 버전의 공식 핸드오프와 최종 판단 기록을 차단하고, 탐색용 미리보기에는 기준 상태를 표시한다.
- **검토 속도:** 지원서 1건당 근거 확인과 판단 사유 기록 시간을 기존 방식과 비교해 측정한다. `2분 이내`는 측정 전 확정 목표가 아니라 보조 검증 지표로 둔다.
- **대량 입력:** 발표 데모에서는 20건 입력을 처리하고 진행 상태 또는 오류 상태를 사용자에게 보여야 한다. 200건은 후속 확장 목표다.
- **감사 가능성:** 기준 버전, 검토자, 판단 사유, 참조 근거, 변경 시점을 기록해야 한다.
- **데모 데이터 안전:** 발표에서는 비식별 또는 합성 지원서 데이터를 사용한다. 실제 개인정보를 사용하지 않는다.

[ASSUMPTION] 5일 안에는 다중 테넌시, SSO, 외부 ATS 연동, 운영 수준의 보존 정책, 실제 고객 온보딩을 구현하지 않는다. 발표용 제한 환경에서 핵심 가치만 검증한다.

[ASSUMPTION] 발표 데이터는 개인정보가 제거된 합성 PDF 지원서 20건과 기준 교정용 표본 3~5건으로 구성한다. 실제 지원서와 실명은 사용하지 않는다.

## 8. 성공 지표와 역지표

### 성공 지표

- 대표 검토 흐름에서 지원서 1건당 근거 확인과 판단 사유 기록 시간을 기존 방식과 비교해 측정한다.
- 발표용 입력 20건 모두가 기준별 근거 매핑 또는 `근거 없음` 상태를 갖는다.
- 검토되지 않은 지원서가 결과 화면에서 조용히 누락되지 않고 처리 상태를 확인할 수 있다.
- 모든 공식 핸드오프 카드가 승인된 기준 버전 ID를 참조한다.
- 두 검토자의 불일치가 사라지지 않고 충돌 항목과 근거로 표시된다.
- 교정 게이트에서 두 검토자의 불일치 항목을 식별하고 승인된 기준 버전을 생성할 수 있다.
- 매핑 결과의 기준별 인용구를 선택하면 스니펫·페이지·주변 문맥이 표시된다. 좌표 기반 하이라이트는 가능한 입력에서만 추가 제공한다.
- 핸드오프 카드만으로 현업 리더가 지원자의 근거, 우려, 인터뷰 질문을 파악할 수 있다.
- 발표 시나리오에서 입력 지원서 묶음이 승인 기준 버전, 매핑 근거, 결정 로그와 누락 없이 연결된다.

### 역지표

- 원문 위치가 존재하지 않거나 인용구와 실제 원문이 불일치하는 매핑 비율
- 승인되지 않은 기준으로 생성된 검토 카드 수
- 자동 랭킹·자동 합격/탈락으로 오해될 수 있는 UI 상호작용 수
- 두 검토자의 충돌이 기록 없이 사라지는 비율
- 핸드오프 카드가 Slack 등 별도 채널의 재작업을 유발하는 비율

## 9. 발표·제출 요구사항

### 발표 제약

- 발표: 5분
- 질의응답: 5분
- 데모 영상: 1~2분
- 핵심 데모는 실제 입력 → 처리 → 출력 화면을 보여줘야 한다.
- 실제 클릭 가능한 데모가 최우선 산출물이다.

### 필수 제출물

**DEL-001 문제 정의 카드**

병목을 한 문장으로 제시하고, 근거 숫자와 출처, 이번 MVP에서 풀지 않은 것, 성공의 정의를 포함해야 한다. 숫자와 출처는 확정 전까지 임의로 작성하지 않는다.

#### 문제 카드용 근거 후보 — 검증 전

- SHRM 2025 채용 벤치마크는 2,300명 이상의 SHRM 회원 응답을 바탕으로 하며, 56%의 채용 리더가 인재 부족을 문제로 꼽고 비임원·임원 채용의 중간 time-to-fill이 대략 한 달 반이라고 보고한다. 이는 채용 전반의 압박을 보여주는 거시 근거이지, 서류 검토 시간의 직접 근거로 사용하지 않는다. 출처: [SHRM State of Recruiting 2025](https://www.shrm.org/executive-network/insights/people-strategy/state-of-recruiting-2025-insights-to-maximize-recruitment)
- University of Washington의 이력서 가이드는 TheLadders의 시선 추적 연구를 인용해 채용 담당자의 초기 이력서 검토 시간이 평균 6초였다고 설명한다. 다만 연구 표본은 전문 채용 담당자 30명, 10주 관찰이며 미국·과거 연구라는 한계가 있으므로 한국 채용 시장의 대표 통계처럼 말하지 않는다. 출처: [University of Washington Resume Guide](https://hasc.washington.edu/sites/default/files/2023-09/HAS%20Resume%20Guide.pdf), 원 연구가이드 인용: TheLadders.
- 데모 자체의 근거 숫자는 “동일 지원서 묶음에서 범용 LLM과 본 시스템이 원문 위치를 정확히 연결한 비율 및 검토 완료 시간”으로 측정하고, 측정일·입력 수·프롬프트·판정 기준을 함께 기록한다.

**DEL-002 설계 요약 1장**

담당자가 결과를 믿게 만드는 장치와 오판 대응 방식을 설명해야 한다. 승인된 기준 버전, 원문 인용구·위치, 검토자 간 불일치 표시, 자동 결정 금지 가드레일을 포함한다.

**DEL-003 베이스라인 비교 컷 1장**

동일한 입력을 범용 LLM에 그대로 넣은 결과와 본 제품 결과를 나란히 비교한다. 원문 근거·위치·기준 버전·의견 차이·결정 로그가 무엇을 다르게 만드는지 한 화면에서 보여줘야 한다.

**DEL-004 레포지토리 및 배포 링크**

심사자가 데모를 재현하거나 결과를 확인할 수 있도록 저장소 링크와 배포 링크를 제공한다.

### 발표 성공 정의

- 심사자가 1~2분 영상만 보고도 실제 입력부터 근거 기반 출력까지의 흐름을 이해한다.
- 문제 정의 카드가 “왜 필요한가”를 숫자와 출처로 설명한다.
- 설계 요약이 “왜 믿을 수 있는가”와 “오판 시 어떻게 드러나는가”를 설명한다.
- 베이스라인 비교 컷이 범용 LLM과의 차이를 추가 설명 없이 보여준다.
- 발표 시점에 클릭 가능한 데모, 레포, 배포 링크가 모두 접근 가능하다.

## 10. 수상 관점의 제품 포지셔닝

- **비욘드 브리프 상:** 자동 선발이 아니라 기준 교정·근거 매핑·판단 이력이라는 답지 밖의 접근을 선명하게 보여준다.
- **비즈니스 포텐셜 상:** 채용 검토 시간과 서류-현업 핸드오프 비용을 줄이는 B2B 업무 흐름으로 확장 가능성을 설명한다. 시장 규모나 고객 수는 근거 없이 주장하지 않는다.
- **빌더스 초이스 상:** 참가자가 짧은 시간 안에 이해하고 직접 사용해볼 수 있는 직관적인 데모를 우선한다.
- **0→100 상:** 5일 동안 문제 정의에서 실제 입력·처리·출력 데모까지 도달한 성장폭을 증거로 남긴다.

## 11. 발표 시나리오 초안

1. **문제 정의 카드:** 대량 지원서 검토의 병목과 기존 방식의 손실을 한 문장·숫자·출처로 제시한다.
2. **실제 데모:** 승인된 기준 버전을 확인하고 지원서 입력을 시작한다.
3. **근거 매핑:** 기준별 원문 인용구를 클릭해 스니펫·페이지·주변 문맥을 보여주고, 가능한 입력에서는 위치 하이라이트를 추가로 보여준다.
4. **판단 핸드오프:** 의견 차이, 판단 사유, 미검증 질문이 카드로 전달되는 장면을 보여준다.
5. **베이스라인 비교:** 같은 입력을 범용 LLM에 넣은 결과와 나란히 비교해 신뢰 장치를 설명한다.
6. **마무리:** 자동 합격·탈락을 하지 않는 이유와 다음 확장 방향을 설명하고 레포·배포 링크를 제시한다.

## 13. 위험과 미결정 사항

- 지원서 PDF·문서 형식별로 페이지·문단 좌표를 얼마나 안정적으로 보존할 수 있는가? 실패 시 스니펫·페이지·주변 문맥 fallback이 작동하는가?
- 원문 인용구의 정확성을 어떤 샘플링 기준과 검수 절차로 확인할 것인가?
- 4가지 검토 상태의 정확한 명칭과 의미는 무엇인가?
- 지원서 20건을 실제 처리할지, 사전 처리된 데모 데이터와 진행 상태를 사용할지 결정해야 한다.
- 발표용 직무·지원서 데이터는 백엔드 개발자·합성 PDF 20건을 기본값으로 사용하며, 실제 데이터가 확보되면 교체한다.
- 문제 정의 카드에 사용할 근거 숫자와 신뢰할 출처를 확정해야 한다.
- 범용 LLM 베이스라인에 사용할 동일 입력, 모델, 프롬프트, 비교 기준을 고정해야 한다.
- 레포지토리와 배포 링크의 공개 범위 및 재현 절차를 결정해야 한다.
- 발표 시나리오에서 실제로 클릭할 기능과 영상에서만 보여줄 기능을 구분해야 한다.
- `2분 이내`를 보조 지표로 사용할 때 비교 기준과 측정 방법을 확정해야 한다.
