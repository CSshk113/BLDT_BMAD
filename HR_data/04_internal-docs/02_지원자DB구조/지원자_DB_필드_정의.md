# 지원자 DB 필드 정의

> `01_ledger/지원접수원장_178건.csv` 는 이 DB에서 뽑은 것입니다.
> 각 컬럼이 원래 어떤 필드였고, 어떤 값을 담으며, 누가 채우는지를 정의합니다.
> 값의 **의미**는 `03_스크리닝판정기준/` 두 문서가 담당합니다 — 여기는 **구조**만 다룹니다.
> 아래 엔트리는 전부 **더미 데이터**입니다.

---

## 1. 구조 — 지원자 1명 = 1행 + 페이지 본문

지원자 한 명이 **하나의 행**이고, 그 행에 딸린 **페이지 본문**에 면접 가이드·면접 기록 같은
긴 문서가 들어갑니다. 트래킹 속성과 서술형 기록을 한 곳에서 보기 위한 구조입니다.

```
[한 행 = 지원자 1명]
 ├─ 트래킹 속성  ── 이름·채널·지원일·포지션·현황·단계별 판정  ← 원장 CSV로 추출되는 부분
 └─ 페이지 본문  ── 면접 가이드 / 면접 기록 / 인사이트 보고서 / 레퍼런스 기록
```

> 과거에는 **전형 트래킹 DB와 서류 전형 기록 DB를 relation으로 연결한 2개 구조**였습니다.
> 한 지원자의 상태가 두 곳에 흩어져 한눈에 보이지 않고 동기화가 번거로워
> **단일 DB + 페이지 본문**으로 통합했습니다. 지금 구조는 그 결과입니다.

## 2. 속성 스키마

| 속성명 | 타입 | 옵션값 / 형식 | 채우는 주체 | 설명 |
|---|---|---|---|---|

| ID | `auto_increment_id` | 1, 2, 3 … | 자동 | 접수 일련번호 |
| 채용 채널 | `multi_select` | 원티드 / 그룹바이 / 링크드인 / 원픽-잡코리아 / 잡코리아 / 사람인 | 접수 | 유입 경로. 아래 §3 참고 |
| 지원일 | `date` | YYYY-MM-DD | 접수 | **접수일이 아니라 지원자가 실제 지원한 날** |
| 포지션 | `select` | B2B 영업 매니저 (5년 이상) / B2B 영업 매니저 (3년 이상) / 교육운영매니저 / B2G 리드 / 마케팅 매니저 | 접수 | 직군 추가 시 옵션 확장 |
| 현황 | `status` | 지원 → 서류 심사 진행 · GP 역량 평가 진행 · 1차 면접 진행 · 레퍼런스체크 진행 · 2차 면접 진행 → 인재풀 등록 · 종료 · 미채용 · 채용 | 단계 진행 시 | **지금 어느 단계에 있는가** |

| 서류심사 | `select` | 불합격 / 합격 (비대면) / 합격 (대면) / 합격 (사내추천) / 합격 (내부채용) / 합격 (외부소싱-채용플랫폼) | 하이어링 매니저 | 2단 판정의 **결론**. 단일 선택 |
| GP평가 | `select` | 불합격 / 평가거절 / 합격 / 보류 / 미실시 | 평가 결과 | 합·불 아님. 면접 참고 자료 |
| 1차면접 | `select` | 불합격 / 면접거절 / 전형중단 / 합격 / 합격 (비대면) / 합격 (대면) | 면접 후 | |
| 레퍼런스 | `select` | 불합격 / 진행거절 / 전형중단 / 미실시 / 완료 | 진행 후 | |
| 2차면접 | `select` | 면접거절 / 전형중단 / 불합격 / 합격 | 면접 후 | |
| 채용 서류 | `text`(링크) | 이력서 파일 링크 | 접수 | 원본 이력서 위치 |
| 불합격 안내 | `checkbox` | ☑ / ☐ | HR 담당자 | 불합격 통보 발송 여부 |

**설계상 중요한 두 가지**

1. **`현황`(지금 어디에)과 단계별 판정(그 단계의 결과)은 별개 필드입니다.**
   `현황 = 종료` 여도 어느 단계에서 왜 끝났는지는 각 단계 필드를 봐야 알 수 있습니다.
2. **`서류 전형`(근거)과 `서류심사`(결론)가 분리돼 있습니다.**
   근거는 복수, 결론은 단일 — "왜 그렇게 판단했는가"를 잃지 않으면서 다음 행동은 하나로 정합니다.

## 3. 채널 값에 대한 주의

- **`원픽-잡코리아` 와 `잡코리아` 는 서로 다른 채널입니다.**
  앞은 잡코리아 지원서가 자사 지원자 관리 화면으로 들어오는 경로, 뒤는 일반 공고에서 오는 경로입니다.
  **지원 방식이 다르므로 합쳐서 집계하면 안 됩니다.**
- 지원자 관리 시스템(ATS)을 거쳐 들어온 건은 **ATS 이름이 아니라 실제 유입 채널로 변환해** 기록합니다.
  "어느 ATS를 통과했는가"가 아니라 "지원자가 어느 공고를 보고 왔는가"가 채널이기 때문입니다.

## 4. 원장 CSV 컬럼 대응

| CSV 컬럼 | 원 필드 | 비고 |
|---|---|---|
| `ID` | ID | 접수 일련번호 |
| `채용 채널` · `지원일` · `포지션` · `현황` | 동명 | |
| `이름` | 이름 | `후보NNN` 으로 치환. **같은 사람의 재지원은 같은 토큰** |
| `HR` | HR-스크리닝 | `Yes` = 탈락 / `No` = 통과 |
| `불합격 사유` | HR-스크리닝 | 복수 사유는 쉼표로 이어짐 |
| `서류심사` · `1차면접` · `2차면접` | 동명 | 빈 값 = 그 단계까지 가지 않음 |
| `최종결과` | — | 채용·미채용 확정일 |

> `GP평가` · `레퍼런스` · `서류 전형` · `HR 메모` 는 원장 CSV에 포함되지 않았습니다.
> 필드는 존재하지만 판정 재현에 필요한 최소 컬럼만 추출했습니다.

## 5. 아웃바운드는 이 DB에 없습니다

공고를 보고 지원한 사람만 이 DB에 들어옵니다. **직접 찾아가 접촉한 후보(아웃바운드 소싱)는
지원자가 아니므로 별도 트랙으로 관리**하며, 원장 178건에도 포함되지 않습니다.

- 아웃바운드 후보는 이력서가 없는 상태에서 시작하는 경우가 많고, 판정 어휘도 다릅니다
  (합·불이 아니라 `제안 후보 / 검토 필요 / 커피챗 / 보류 / 제외` 같은 접촉 단계).
- 제안을 수락해 정식 전형에 합류하면 그때 지원자 DB로 들어옵니다.
  원장의 `합격 (외부소싱-채용플랫폼)` 이 그 경로입니다.
